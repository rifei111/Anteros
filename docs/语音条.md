## 0. 一页结论

- 语音条不是新的消息类型，而是**一条文本消息带一个音频附件**。模型永远只看 `text`——
  记忆、检索、上下文装配、撤回、搜索的复杂度全被挡在门外。
- **收和发都是「先文本、后补丁」**：先落文本消息并推 `event.message`，外部 IO 完成后重推同 id。
  渲染层 `app.ts` → `upsertMessage` 就是按 id 做 `{ ...item, ...message }` 合并的，所以
  `chat.ts` 的分条循环不等任何外部 IO，气泡时刻不变。**副作用要说清楚**：出站语音在补丁到达时，
  是同一条气泡**长出**一条播放条，不是多发一条消息（5.1）。
- 补丁模式有四个已知代价，都是本期的前置修复项，不是"以后再说"：
  1. `upsertMessage` 在判断 `exists` **之前**就 `unread + 1`（且只在 `document.hidden` 时），
     同 id 重推会重复计未读——**修在 P0**，因为第一次补丁出现在 P2；
  2. 记忆抽取 `void ports.memory.extract(...)` 在 `planReply` 之前就被 fire-and-forget 派发，
     语音消息会连着两遍吃到占位符（详见 7.3）；
  3. 预算闸 `checkBudget()` 只在生成前查"本月是否已达上限"，记账在投递之后，
     所以**音频的钱是花完才进账**：不在每次合成前用估算价预检，硬上限就会晚一轮（10.6）；
  4. `event.typing` 现在只有 `start | stop` 两态，而转写那 10 秒既不是"开始打字"也不该被当 stop
     熄灭——需要第三个态 `transcribe`，内核与渲染层**同一个 PR**改（7.2、13 节）。
- 供应商的全部知识在插件里（`core.media` 从占位填实到 0.2.0）。内核只做五个原语：
  存字节、取字节、转调用、回写元数据、回收文件。
  **只有"这条要不要发语音"必须留在内核**，因为它要的 mood/energy/presence/relation
  在 `PluginApi` 的 13 条方法里一条都读不到（第 4 节末尾把这个取舍讲开）。
- 边界要诚实：插件是**受信进程**，`net.allow:` / `fs.*` 在内核里没有任何运行期执行点；
  真正不可信的是渲染进程。所以客户端永远只提交 `uploadId`，路径一律内核自己生成。
- 同意这块本期**不动全局声明版本**：启用语音的实质门槛是给它授权
  `secrets.read:media.api_key`，而那条权限在现成代码里就已经要求一次性确认 token（12.2）。
  升全局版本的代价是"包括从不点麦克风的人，全部被挡一次重勾九条"，写在 12.2 里留给作者判断。
- **「听起来像人」是这次真正要买的东西，不是"消息附件"**。所以第 10 节把试听提到第一天：
  拿 10 条真实回复、两家供应商、戴耳机听。过不了 7/10 这条线，TTS 就不该进本期。
- P0–P2 不需要任何供应商即可验收；P3 之后的一切都取决于第 10.4 节的试听结论。

## 1. 范围

做：

1. 你按住说话发一条语音条，它听得懂（ASR 转写进上下文）。
2. 它回话时**看场合**带语音条（TTS），音色在插件配置里，发不发由内核策略算。
3. 语音条显示波形、时长、播放进度，可展开/收起转写文字。
4. 媒体文件生命周期：孤儿回收、撤回、配额、丢失探测。
5. 私聊与群聊一致；语音条参与撤回与搜索的既有语义。

不做：

- 外部通道（微信）的语音收发。入站是加密 SILK `.dat`，出站没有可靠手段；
  且 `ChannelInboundMessage` 与 `plugin.channel.send` 的 params 都只有 `text`，
  动它们属于通道契约变更，不在本期。
- 图片消息（`attachment.kind` 预留 `"image"`，本期不实现）。
- 本地离线引擎（whisper.cpp / Piper）。将来走现成的 `runtime_env` 机制（`docs/插件.md` 第 7 节）。

写文档和写 PR 描述时，引用代码的方式统一为：

```

```

而这段代码的语义一个字都没变。符号会改名字（改名字时文档必须跟着改，这是好事，会痛），
行号只会静悄悄错位。

配套规则一：附录 A 的核验脚本已经落成 `scripts/verify-voice-baseline.mjs`，它就是这份文档的**测试**。
每次 rebase 到新版本、每次开工前跑一遍。FAIL 不一定代表文档错了，也可能代表代码已经领先于文档——
两种情况都要在动手前处理掉。

配套规则二：**界面可见的字面量只在定义处写一次**。占位符这类字符串以前在这份文档里出现过两种写法
（`[语音 12"]` 用 ASCII 引号、`[语音 12″ 没听清]` 用 U+2033），而临时气泡是靠
`item.text === message.text` **逐字相等**才摘除的，一个引号差就是两条气泡。
所以从现在起，除 `shared/voice.ts` 里 `voicePlaceholder()` 的定义处之外，
文档、注释、测试里一律写调用形式 `voicePlaceholder({ durMs: 12_000 })`，不手写字面量。
群友那条同规则（`foreignVoicePlaceholder()`）。上面举例的两个字面量是这条规则的举证，
全文只在这里出现一次；正文其它地方（5.3、7.3、12.1）都改成调用形式。

## 4. 四处进不了插件的边界

1. **界面**：渲染进程唯一出口是 `ClientBridge.invoke<KernelMethod>`（`shared/client-api.ts`），
   只能调内核方法表；`KernelApi` 的 `plugins.*` 全是管理方法
   （`list/enable/disable/grant/config.put/restart/secret.*/runtime.*`），
   **没有一条能把调用转发给任意插件**；`plugin.ui.panel.render` 返回只读 JSON 块，
   而客户端渲染层没有任何一处消费它（`grep -rn "panel.render" packages/client/src` 为 0）。
2. **写库**：内核是唯一 SQLite 写入者（`docs/架构.md` 第 4 节）。`messages` 表没有附件列
   （`db/schema.ts` → `messages`），而插件根本连不上这个库。
3. **能力白名单**：`shared/manifest.ts` → `CAPABILITIES` 是硬编码 13 项。多一个字符串，
   整份 manifest 被 zod 拒收，插件连注册都做不到。
4. **字节中转**：插件的 `ANTEROS_DATA_DIR` 是 `<dataDir>/plugins/<id>`，渲染进程是
   `sandbox: true` + `contextIsolation: true`，页面拿不到也没有文件系统权限。

**第 4 条不要拿来当卖点。** 核实结果：`_sdk/plugin-runtime.mjs` 自己就 `import fs from "node:fs"`，
没有任何拦截；`packages/kernel/src` 里对 `net.allow:` / `fs.read:` 也搜不到运行期执行点。
`docs/安全.md` 第 4 节自己写着"声明 + 授权 + 审计，不是操作系统级沙箱"。
所以正确的表述是「**渲染进程不可信，插件被信任**」，本方案据此定两条规矩：

- 客户端永远只提交 `uploadId`，不提交路径；路径由内核生成、内核自己映射。
- 内核→插件传**已校验的 media 目录内相对路径**（ASR 用，省一次 base64 往返）；
  插件→内核传 base64（TTS 用）。方向不同各有理由，不追求对称。

**「那能不能做成一个扩展文件，别写进核心？」**（本轮追问，答案是"半分"）

核实过的事实：内核**没有任何 hook / middleware / interceptor / pipeline 机制**
（`grep -rnE "\bhook\b|middleware|interceptor" packages/kernel/src` 为 0），插件能调的方法一共 13 条
（`shared/rpc.ts` → `PluginApi`：describe / health.check / llm.generate / extract.memory /
world.info / channel.read_since / channel.send / channel.download_media / channel.lease.begin /
channel.lease.end / channel.disable_and_restore / ui.panel.render / notify.send），
投递是写死在 `ChatService.send` 里的
`INSERT → emit("event.message") → emit("event.part") → onPart 回调` 直线。
所以"发语音之前插一个插件钩子"这件事在当前架构里**没有可以挂的地方**。

能扩展的部分确实能扩展，而且已经全在这份方案里了：

| 内容 | 放哪 | 内核里的量 |
| --- | --- | --- |
| 供应商协议、鉴权、音色、语速、重试、单价 | 插件 `core.media`（独立进程，用户可见、可关） | 0 |
| 音频字节与元数据的存/取/校/回收 | `services/media.ts`（新文件，除它以外没有第二个地方碰音频） | 新文件，不改别人 |
| 「这条要不要发语音」 | 内核 `expression/voicePolicy.ts`（新文件，纯函数） | 调用点 1 处 |
| 语音消息的存储 | `messages.attachment` 一列（JSON） | 一处读写映射 |

为什么策略那半进不了插件：它要的输入在 `PluginApi` 里**一条都读不到**。
`WorldState.moodValence / moodArousal / energy / presence` 和 `RelationState.stage`
是内核内存与库里的状态；插件侧那个 `plugin.world.info` 名字像但不是——它的入参是
`{kind: "time" | "weather" | "news"}`，返回 `WorldInfoItem[]`，问的是"外面几点、天气、新闻"，
不是"她现在情绪怎么样"（`shared/rpc.ts` → `PluginApi["plugin.world.info"]`）。
要让它能判，就得开一条"把内心状态暴露给插件"的新能力，那是一条比语音条本身大得多、
而且默认权限更高的口子（任何插件都能读人设与情绪）。本期明确不开。

结论：**扩展形态是 1 个新内核文件 + 1 个新插件 + 1 个新表列，改动面收在三处；
代价是策略那一步必须在核心。** 如果作者更看重"核心零改动"，那就得接受退化的策略
（插件只看文本长度和自己的 config，拿不到 mood/relation/presence），
那是另一个方案，10.1 的产品效果会明显差一档——这个取舍写在 17 节，不在这里替他决定。

## 5. 数据契约

### 5.1 `MessageAttachment` 与状态机

```ts
/** packages/shared/src/domain.ts：ChatMessage 追加 attachment?: MessageAttachment | null */
export interface MessageAttachment {
  kind: "audio";                 // 预留 "image"，本期不实现
  path: string;                  // 内核生成的相对路径，形如 voice/2026-11-01/<hex>.webm
  mime: string;                  // audio/webm;codecs=opus / audio/ogg;codecs=opus / audio/mpeg / audio/wav
  bytes: number;
  durMs: number;                 // 0 = 尚未测得（出站补丁前、以及出站首播前都是 0）
  peaks: number[];               // 24 格 0–1；空数组 = 尚未测得
  transcript?: string;           // 语音→文字时是转写；文字→语音时是朗读稿，见 9.3
  transcriptKind?: "asr" | "shown"; // asr = 机器转写，可能错，见 5.3
  state: "pending" | "ready" | "skipped" | "missing";
  error?: string;                // 人话失败原因，界面直接显示
  costCny?: number;              // 插件回报的费用，见 10.5
}
```

`CostKind` 增加 `"asr" | "tts"`。

状态机（这条替掉 v2 里 §6.3 和 §8.3 互相矛盾的两套说法）：

```
入站（你发的语音）
  media.upload 已经落盘 → chat.send 的 INSERT 就带 { kind:"audio", state:"ready" }
                             durMs 由录音计时给（9.2），peaks 由 AnalyserNode 给（9.3）
  ASR 回来   → UPDATE transcript（state 不变，仍是 ready）
  ASR 失败   → UPDATE error（state 仍是 ready：文件在，能重听，能重试）

出站（它发的语音）
  策略判定要发 + 预算预检通过（10.6）→ INSERT 就带 { kind:"audio", state:"pending", durMs:0, peaks:[] }
  TTS 成功   → UPDATE path/bytes/mime/state: pending → ready；durMs/peaks 由渲染层首播前解码回填（9.3）
  TTS 失败/超时 → UPDATE state: pending → skipped, error（不写 path，不假装有声音）
  预算预检不过 → **根本不写附件**（连 pending 都不该出现，见 7.4）

公共
  ready → missing 只由 GC 或"文件不在了"探测触发
  kind 一旦写入永不改；attachment 列为 NULL 才是普通文本消息
```

**补丁到达时界面发生什么，说清楚（v3 在这句上撒过谎）**：出站语音不是"先打字、再补一条语音"，
而是**同一条气泡长出一条播放条**——消息 id 不变、位置不变、`text` 一个字不变。
`pending` 和 `skipped` 都渲染成纯文字气泡，所以用户看到的是"这条消息过了一下多出一根可以点的条"，
而不是两条消息。要说"多发一条"只有一种做法：真 INSERT 第二条消息——那会同时打乱
`part_index`、`event.part` 的 `index/total`、微信 `onPart` 投递与撤回的按 turn 分组，本期不走。

长度与波形在补丁那一刻可能是 0：`durMs === 0` 不显示秒数，`peaks` 为空显示等高灰格，
渲染层随即预取一次字节解码回填（9.3），回填是第二次同 id 补丁。两次补丁都在 13 节的幂等面里。

### 5.2 上传握手

v1 让客户端把 `attachment` 整体传进 `chat.send`，等于允许渲染进程指定任意 `path` 写进数据库。改成两段：

```
media.upload {eventId, dataBase64, mime, durMs, peaks}
  → 内核校验（7.5）→ 落盘 → 返回 { uploadId, attachment }   // path 由内核生成
chat.send {text, uploadId}
  → 内核把 uploadId 对应的附件挂到这条消息，uploadId 立刻作废
```

`uploadId` 是随机 hex，内核在 `media/.pending/` 里维护 15 分钟映射；过期未绑定的进 7.6 的 GC 队列。

### 5.3 `text` 的语义，以及"这句话到底是谁说的"

语音消息的 `text` 存转写文字；未回来或失败时存占位符。既有链路因此零改动：抽取读 `text`、
装配读 `text`、`recall()` 与复制读 `text`。

三条必须一起定的细节：

1. **占位符由谁生成**：`app.ts` → `upsertMessage` 摘"发送中"临时气泡的条件是
   `item.text === message.text`。也就是说客户端乐观插入的临时气泡和内核回声的 `text` 必须逐字相等，
   否则同一条语音在列表里躺两条。所以占位符模板只有一份：`packages/shared/src/voice.ts`（新）
   的 `voicePlaceholder({ durMs })`，客户端与内核各调一次同一个纯函数（第 2 节配套规则二）。
2. **转写不是用户原话**：ASR 结果进记忆时是机器听写的，可能错字、可能漏后半句。
   `MemoryPort.rememberEpisode` 的 `source` 枚举现有 `"user_said" | "it_did" | "world" | "inference"`。
   本期不扩枚举，用 `confidence` 降一档 + `sourceRef` 里带 `{ transcribed: true }` 表达，
   并在 7.3 里把它接到 `extract` 的入参上。
3. **占位符不进模型**：语音消息一定先转写、后回复（7.2），所以正常路径下 `planReply`
   看到的是真转写文本。只有 ASR 失败时才会带着占位符走到回复分支，那种情况按 11.2 处理
   （本地短句池，不调模型），不把 `voicePlaceholder({ durMs })` 的输出喂给模型去"发挥"。

### 5.4 schema 迁移

`messages` 加一列 `attachment TEXT`（JSON），`db/schema.ts` → `SCHEMA_VERSION` 3 → 4。
迁移照抄 sender_name 那两列的幂等写法（`db/database.ts` 里
`if (!columns.has("sender_name")) this.handle.exec("ALTER TABLE messages ADD COLUMN sender_name TEXT")`）。
`ChatService` 的 `MessageRow` 与 `toChatMessage()` 各加一个字段映射（JSON.parse 失败要当成 null，
不能一条脏数据把整个历史查询炸掉）。

### 7.2 `chat.send` 的入参与「先转写再回复」

`shared/rpc.ts` → `KernelApi["chat.send"]` 的 params 增加可选 `uploadId: string`；
result 增加可选 `reason?: string`（11.2 要用）。

时序：

```
chat.send(uploadId)
  ├─ epoch+1、INSERT user（text = voicePlaceholder({ durMs })，attachment = ready）
  ├─ event.message                        ← 气泡立刻出现，带波形
  ├─ event.typing { state: "transcribe" } ← 转写窗口不空（见下，客户端要同步加 case）
  ├─ 不派发 extract（见 7.3）
  ├─ media.transcribe → plugin.media.listen（上限 10s）
  │     ├─ 成功：UPDATE text = 转写、attachment.transcript；event.message 重推同 id
  │     │        → 这时才 extract（真转写，标 transcribed）
  │     └─ 失败/超时：UPDATE attachment.error；event.message 重推；按 11.2 走"没听清"分支
  ├─ checkBudget()                        ← 现状那一次，管模型的 token 钱
  ├─ planReply（只看 text，逻辑零改动）→ parts + fullText
  ├─ voicePolicy(fullText, world, relation)（10.1）→ 该不该发语音
  ├─ 要发：checkBudget(estimateSpeakCostCny(fullText))（10.6）→ 生成朗读稿 →
  │        失败/超预算就整段跳过，下面当没发生过
  └─ 分条循环（ChatService.send 里的 `for (let index...)`）：
        每条原样 INSERT 文本、推 event.message、await sleep(typingMs)
        第一条 part 的 INSERT 额外带 attachment = { state:"pending" }（渲染仍是纯文字，5.1）
        TTS 在循环外异步跑：成功 → 补丁 ready（第一条气泡长出播放条）；失败 → skipped
```

顺序里有一处**不能换**：预检排在朗读稿改写之前。朗读稿本身是一次真实的模型调用，
预算见底时先花它再拦 TTS，等于买了个用不上的稿子（10.2 复述了同一条）。

ASR 串在回复前面，用户会觉得"它听完才回"，这正是真人节奏；而且 `kernel-client.ts`
给 `chat.send` 的超时是 120s（`METHOD_TIMEOUT_MS`），装得下一次转写。

**转写那 10 秒不能是空窗（本轮新增）**：v3 把上限写成 20s，而且整个窗口里没有 typing、
没有进度、没有任何反馈——用户按完说话只看着一条不带文字的气泡停 20 秒，第一反应是软件死了。
定两条：

1. **上限从 20s 压到 10s**（`plugin.media.listen` 侧，与 7.8 表对齐），到点走 11.2 的
   "没听清 + 可重试"。60s 语音在主流兼容接口上正常 1–3s 出结果，10s 已是三倍余量；
   真等不到，重试比干等诚实。
2. **等待分成两段，各用各的指示器**（这是你那条「在转写期间就该起 `event.typing`」的落地方式）。
   直接复用 `event.typing {state:"start"}` 会有一个语义 bug：`start` 在现契约里带着
   `plannedChars` / `plannedMs`，客户端把它演成「正在输入…」——三个跳动点，悬停标题是
   "内核预计打字 N 秒"（`ChatPane.tsx` 里那段 `typing-bubble`）。
   转写那一段并不是它在输入，是它在**听你刚才说的话**；而且 `plannedMs` 在这段根本没有值可填，
   悬停会显示"预计打字 0 秒"之类的假信息。把两段都说成"正在输入"，等于用界面撒第一次谎。

   定成两个态，事件不换：

   | 段 | 内核发什么 | 界面显示 | 现成契约够不够 |
   | --- | --- | --- | --- |
   | 转写中（≤10s） | `event.typing { state:"transcribe" }` | 「正在听写…」，不带字数与预估时长 | **不够**，见下 |
   | 生成+打字（现状） | `event.typing { state:"start", plannedChars, plannedMs }` → 投递后 `{ state:"stop" }` | 「正在输入…」 | 够，原样不动 |

   这样分还守住了 `ChatPane.tsx` 顶部注释里那条既有纪律：
   「**「正在输入…」只在 `event.typing` 说 true 时出现，不自己造计时器**」。
   所以"正在听写"同样必须由内核事件驱动，不能在渲染层"发完语音就假装转圈 3 秒"——
   那正是这条注释要防的东西，也是客户端不许自己估时长的同一条理由（规范 1 §4）。

   要动的只有两处，都不碰既有语义：
   - `shared/rpc.ts` → `KernelEvents["event.typing"]` 的 `state` 联合类型加 `"transcribe"`
     （P0 契约那一行顺手加）；
   - `app.ts` → typing 分支加一个 case：置 `thinking: true`，收到 `start` 时切成 `typing`，
     收到 `stop` 时清空。现有实现是"start 置真、**其它一切落进 else 清空**"
     （`setState(previous => …)` 那一段没有第三种分支），所以这是个真坑：
     **只改内核不改客户端的话，`transcribe` 会走进 else 把指示器关掉**，
     加了这个事件反而比不加更空。客户端那行必须和内核那行同一个 PR 里合。
   转写结束**不发 stop**，直接由 `planReply` 那段的 `start` 接手，两段之间不闪。
   入站预算预检不过时（10.6）也一样：`transcribe` 不发，麦克风在 pointerdown 就已经置灰了。

v1 那套「TTS 在 `sleep(typingMs)` 前 fire、之后 await、超时 `min(typingMs+3000, 15000)`、
成功才 INSERT」整段作废：那会让首条气泡等 TTS，最坏迟到十几秒。

### 7.3 记忆抽取不能吃到占位符（v2 漏了，是真硬伤）

现状：`ChatService.send` 在 INSERT 用户消息之后、`planReply` 之前，有一行
`void ports.memory.extract(deps.agentId, [{ id, text, ts }], now, conversation)`——
fire-and-forget，不 await。语音消息走到这里时 `text` 还是 `voicePlaceholder({ durMs })` 的输出。

后果：数据库里躺着一排"用户说过占位符"的 episodic 记忆，还会被召回喂进上下文；
`core.memory-extract` 的规则管线更糟，它对时间、数字、人名做正则命中，
占位符里的秒数会当成"用户提到一个数字"抽成语义记忆。**这不是脏数据，是它会说错话。**

改法（三行以内，不做新架构）：

1. `MemoryPort.extract` 的 texts 元素从 `{id, text, ts}` 扩成 `{id, text, ts, transcribed?: boolean}`。
   `transcribed === true` 时，规则管线只跑不依赖字面的部分，LLM 抽取的提示里加一句
   「这是语音转写，可能有错字，不要把措辞当成他的原话」，落库 `confidence` 乘 0.8，
   `sourceRef` 带 `{transcribed:true}`。
2. `ChatService.send` 对带附件且 `transcript` 为空的用户消息**跳过**这一次 extract 派发，
   改到转写落地之后再调一次；ASR 失败则对占位符调一次
   `rememberEpisode({ text: 人话版占位符, importance: "detail", confidence: 低 })`，
   并 `openLoop({ topic: OPEN_LOOP_TOPIC_UNCLEAR_VOICE })`——下次它有机会主动问回来。
   这条用的是现成的 `MemoryPort.openLoop`，不是新接口。
3. **幂等这块本期一行代码都不用写，但有一个必须守住的约束**（本轮核实结果，v3 写错了）：
   - `MemoryService.openLoop` 已经按 topic 去重：命中未闭合的同 topic 环时它更新并再催一次，
     不插新行（`memory/service.ts` → `openLoop`，判重走 `findOpenLoopByTopic`）。
     所以"同一条环不重复"是现成的，**代价全在 topic 常量化上**：topic 必须是常量，
     一旦拼进时长、错误原因或消息 id，判重立刻失效，环表会变成垃圾场。
   - episodic 落库已有"24 小时内同一句话不重复落库"的去重（`memory/service.ts` 里的注释与实现）。
     这条正好覆盖 `media.retry` 的场景：重试转写出同样的文字，第二次抽取不会重复落记忆。
     所以 7.2 的 retry 不需要新的判重键，只要别在文案里加时间戳把它变成"新句子"。

### 7.4 出站补丁的纪律

- 先过两道门才写库：`voicePolicy` 说该发（10.1）**且**预算预检说花得起（10.6）。
  两门任一不过就**不写附件**——连 `pending` 都不出现。预检不过时这条退成纯文字，
  在 `turns` 留一行痕，界面不解释"本来该有语音"（用户从来不知道，就不会有落差）。
- 门过了才 INSERT 时就把 `{kind:"audio", state:"pending", durMs: 0, peaks: []}` 写进 `attachment`。
  **没有估算时长**：v3 的 `estimated` + `durMsEstimate()` 全删，因为没有任何地方消费它——
  `pending` 不渲染条（5.1），渲染只读实测值。字数换秒数这件事仍然要做，但只喂预算预检
  （`estimateSpeakCostCny()`，见 10.6），不进契约、不进界面。
- 补丁**只允许填** `path/bytes/mime/durMs/peaks/state/error/costCny/transcript`，
  **永不改 `kind`**，永不把一条文字消息变成语音消息（5.1 的同一条气泡长出播放条）。
- 一段回复只合成**一段**语音，内容是整条回复的朗读稿（10.2），挂在**第一个 part** 的气泡上。
  选第一条不选最后一条的理由：分条之间有几秒到十几秒的打字间隔，挂在最后一条意味着
  播放条出现在用户已经读完的地方；第一条是视线落点。代价是展开文字与气泡文字不同源，
  所以界面必须说清它是什么——9.3 把标题定成「朗读稿」，不是「文字」。
  原因见 10.1：分条上限 `MAX_PARTS = 20`、每条约 32 字（`MAX_PART_CHARS`），
  逐条合成会造出一串 2 秒的碎音频，既难听又难查。
- TTS 失败/超时：`state → skipped` + `error`，界面上那条从来没出现过语音（5.1），
  记一条 `event.log`，`turns` 里留痕。不重试第二次（本期），成本不记。
- 崩溃遗留的 `pending`：见 7.7。

### 7.5 校验规则

- **魔数**：webm/EBML 是 `1A 45 DF A3`（v1 误写 `1A E3 DF A3`）；OGG 不是 EBML，是 `4F 67 6B 53`（`OggS`）；
  MP3 是 `ID3` 或 `FF FB`/`FF FA`/`FFFx`；WAV 是 `52 49 46 46`（`RIFF`）+ 偏移 8 的 `57 41 56 45`（`WAVE`）。
  **wav 必须在扩展名白名单里**，否则 P0.5 的"手放一个 wav 试播放"没有落盘通道。
- **时长**：内核没有解码器，做不到独立校验 `durMs`。入站信客户端自报（`performance.now()` 计时），
  出站由渲染层解码实测后回写（9.3），**两个方向都是测出来的，没有估算值**。
  内核只做范围合理性检查（`0 ≤ durMs ≤ 60_000 + 容差`，越界当 0 处理）与体积硬上限。
  文档写明"入站时长来自客户端自报，出站时长来自渲染层回填"。
- **上限对齐**：客户端 60s 录音、内核 4MB 体积、`media.load` 返回受 `MAX_FRAME_BYTES`（8MB）约束
  （4MB 的 base64 约 5.3MB，安全）。v1 的「2MB/90s」与客户端 60s 不一致，v3 统一 60s / 4MB。
- **路径**：判定用 `path.relative(mediaDir, target)`，结果为空、以 `..` 开头、或是绝对路径 → 拒。
  **不要用 `startsWith(mediaDir)`**，同级的 `media-evil/` 前缀能绕。
  现成参考：`services/export.ts` → `collectMedia()` 就是用 `path.relative` 归一相对路径的。

### 7.6 `media.gc`（文件生命周期）

| 触发 | 处理 |
| --- | --- |
| `media.upload` 后 15 分钟没绑定到消息 | 删（孤儿） |
| 消息被撤回（`ChatService.recall`） | 删文件，附件置 `{state:"missing", error:"已撤回"}` |
| `memory.reset` | reset 已清整个 media 目录，无需新增 |
| 全局配额（默认 500MB，settings 可调） | 按 `ts` 从旧到新删到阈值以下，被删的气泡转 `missing` |
| 换机/导入后文件不存在 | `media.load` 探测 → 回写 `missing`，界面显示「语音文件已丢失」 |

GC 挂在内核现有定时器上（与 proactive 的 tick 同处），启动后延迟 60s 跑第一次。

顺带记录一个**本期会撞到的既有 bug**：`ChatService.recall` 发的是
`emit("event.recall", { messageId, message: updated })`，而 `shared/rpc.ts` →
`KernelEvents["event.recall"]` 声明的是 `{ messageId, replacement: string }`，
`app.ts` 的订阅者按契约读 `payload.replacement` 并把 `text` 覆盖成它。
撤回一条消息时客户端会拿到 `text: undefined`。做语音撤回（要同时清附件显示）之前先把它对齐，
否则补丁会把气泡改成空白。修法：内核改发 `replacement`（推荐，契约已定），或类型改成
`{ messageId, message }` 并同步客户端——二选一，别两边都留着。

### 7.7 崩溃与重启

`state === "pending"` 落库后进程崩了，重启会永远停在 pending。内核启动时扫一遍
（放 `bootstrap()` 之后、IPC 服务起来之前，避免客户端先看到 pending）：
pending 且无在途任务的行，出站置 `skipped`，入站（文件在、没转写）保持 `ready` 并显示重试。

### 7.8 客户端超时表（v2 没有这条）

`packages/client/src/main/kernel-client.ts` → `METHOD_TIMEOUT_MS` 只给少数方法放宽，
默认 `DEFAULT_TIMEOUT_MS = 30_000`。插件侧 `core.media` 的 `resources.call_timeout_ms` 是 90s，
`CHANNEL_WRITE_TIMEOUT_MS` 也是 90s。**两个时钟不同步**：客户端 30s 就把
`chat.send`（含 ASR）或 `media.synthesize` 判死，内核和插件那边还在等。

本期把三层超时对齐成一张表，外层必须大于内层，否则先死的总是最不该死的那个：

| 层 | 方法 | 值 | 说明 |
| --- | --- | --- | --- |
| 插件调用 | `plugin.media.listen` | 10s | 7.2 的转写上限；到点走 11.2，不让用户干等 |
| 插件调用 | `plugin.media.speak` | 30s | 56 字以内朗读稿，正常 2–8s |
| 插件进程 | `resources.call_timeout_ms` | 90s | 现状，保持不动（最外层兜底） |
| 客户端 RPC | `media.transcribe` / `media.retry` | 20s | 比插件侧 10s 大一倍余量 |
| 客户端 RPC | `media.synthesize` | 45s | 比插件侧 30s 大 |
| 客户端 RPC | `chat.send` | 120s | 现状，覆盖一次转写(≤10s) + 一次生成 + 分条打字 |

`chat.send` 的 120s 是**已经放宽**的现成条目，所以 7.2 把 ASR 串进 `chat.send` 不需要改它；
需要新增的是上表里 `media.transcribe`、`media.retry`、`media.synthesize` 三条。
`media.upload` 走默认 30s 就够（本机具名管道上 5.3MB 的 base64 是几十毫秒量级，
且它是纯本地写盘，不等任何外部 IO）。

```json
    "baseUrl":  { "type": "string", "description": "OpenAI 兼容根地址（可含或不含 /v1）" },
    "ttsModel": { "type": "string" },
    "asrModel": { "type": "string" },
    "voice":    { "type": "string" },
    "rate":     { "type": "number" },
    "maxSeconds": { "type": "number" },
    "asrTimeoutMs": { "type": "number" },
    "pricePerSecondCny": { "type": "number" },
    "pricePerMinuteCny": { "type": "number" }
  }
}
```

`asrTimeoutMs` 默认 10000（7.2 那个上限落在插件里，因为只有它知道自己调的是哪家、
要不要排队重试）；`resources.call_timeout_ms` 保持 90s 不动，它是最外层的兜底，
不是转写的预算。**这两个数不是一个东西**，v3 只写了一个 90s，等于把转写窗口设成 90 秒。

**v1 的 `net.allow:api.openai.com` 删掉**：`baseUrl` 允许填 DashScope / 智谱 / Moonshot / 本地 Ollama，
写死一个域名与之冲突；而 `net.allow` 本来就没有运行期执行点，写一个错的域名只会给用户
"访问被限制了"的错觉。联网范围在 `docs/安全.md` 第 4 节已有的诚实说明里统一交代。

**`baseUrl` 拼接的坑（1.0.18 现成证据）**：`settings.ts` → `DEFAULT_SETTINGS["llm.baseUrl"]`
是 `https://api.deepseek.com/v1`，**已经带 `/v1`**。v2 写的 `POST {base}/v1/audio/speech`
照抄就会拼成 `/v1/v1/audio/speech`。规矩：先剥尾部 `/v1` 与斜杠，再拼 `/v1/audio/...`；
spike 里第一件事就是把这个函数写成纯函数并单测三种输入
（`.../v1`、`.../v1/`、`...`）。

协议按 OpenAI 兼容实现 `POST {base}/v1/audio/speech` 与 `POST {base}/v1/audio/transcriptions`。
出现非兼容供应商时再开新插件，不在这里堆 if。

保留占位实现的两条品质（`plugins/core.media/index.mjs` → `blocked()` 直接搬）：
**未配置** 与 **已配置但缺能力** 分开说；绝不返回假音频、假 URL。

### 8.3 用 `attachments` 当能力开关

```json
{ "ok": true, "status": "ok", "message": "语音插件就绪（tts-1 / whisper-1）",
  "attachments": { "listen": true, "speak": false } }
```

内核透传成 `media.status = { listenReady, speakReady, message }`，界面据此决定麦克风按钮
亮不亮、要不要显示「它回语音」。音色与限速全归插件 config，**内核 settings 只加一个键**
（`media.voiceOutbound`，见 10.1），不往内核里塞供应商相关配置。

配置编辑的现实做法：PluginsTab 那个 JSON 文本框。为了不让用户写坏配置，内核在
`plugins.config.put` 里按该插件 `config_schema` 做一次校验，类型/枚举不符回成人话错误
（现在没有这条校验，列 P3，约 40 行）。不做 schema 渲染表单——那是独立一笔前端工作。

### 8.4 为什么不走多模型的 `audio` 路由

仓库的模型路由确实为音频留了位置：`domain.ts` → `ModelTaskKind` 含 `"audio"`，
`services/models.ts` → `ModelService.resolve(kind)` 收这个枚举，多模型页
（`admin/tabs/MultiModelTab.tsx` → `KINDS`）也把它列出来了，看着更顺。
但那条路由的密钥在 models 条目里、界面在多模型页，而媒体供应商的鉴权与计费口径跟对话模型不同
（按秒、按字符，没有 token）。v3 仍选插件自己的 `media.api_key` + `secrets.read:` 通路
（`plugins/secrets.ts`），`audio` 路由保持现状、不删。将来统一到路由是独立一次重构。

### 8.5 插件进程的根证书

插件是独立 Node 进程，`fetch` 只认 Node 自带根证书；本机有 TLS 中间人代理（安全软件、公司网）时
直接 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`。内核有 `useSystemCertificates()`
（`packages/kernel/src/util/net.ts`），插件没有。修在 `plugins/_sdk/plugin-runtime.mjs`
里做一次 `node:tls` 的 `getCACertificates("system")` 合并，对所有插件都受益。

## 9. 客户端改动

### 9.1 先修 CSP（一行改动、一票否决）

`packages/client/src/renderer/index.html` 的 CSP 有 `img-src 'self' data: blob:`，**没有 `media-src`**。
`URL.createObjectURL` 出来的 `blob:` 塞给 `<audio>` 会落回 `default-src 'self'` 被拦——点着听根本不成立。
补 `media-src 'self' blob:`。排在语音条任何可播放版本之前。

### 9.2 按住说话状态机

`idle → arming → recording → (send | discard)`

- pointerdown：读**缓存**的 `media.status`（9.5），不可用则置灰给「去配置」；
  可用则 `getUserMedia({audio:{echoCancellation:true,noiseSuppression:true,autoGainControl:true}})`，
  mimeType 按 `audio/webm;codecs=opus` → `audio/ogg;codecs=opus` → `audio/mp4` 用
  `MediaRecorder.isTypeSupported` 依次探测。
- **计时**：`MediaRecorder.start()` 前记 `performance.now()`，`stop()` 时相减得 `durMs`。
  别用 `MediaRecorder` 的 `timeslice` 拼时长（不准、受 packet 边界影响），也别指望
  webm 容器里的 duration 字段（Chromium 写实时流时通常不回填，见 9.3）。
- pointerup 在按钮内且 ≥500ms：`media.upload` → `uploadId` → `chat.send`。短于 500ms 丢弃并提示「说得太短」。
- pointerup 在按钮外，或 pointermove 进取消热区：丢弃。**必须监听 window 级 pointerup**，
  只绑按钮会导致鼠标滑出后录音永不停止。
- 60s 硬上限，55s 起警告色与倒计时；`AnalyserNode` 实时驱动波形，停止时从同一路上抽 24 格峰值
  （主路径，见 9.3）。

### 9.3 语音条：peaks 与 durMs 的唯一来源（v3 在这里自相矛盾，本轮定死）

新组件 `VoiceBar.tsx`：波形（`peaks` 驱动，播放进度着色）+ 时长 + 播放态 + 展开区。

每个字段只有一个主路径，其余是兜底：

| 字段 | 入站（你录的） | 出站（它合成的） | 兜底 |
| --- | --- | --- | --- |
| `durMs` | 录音计时（9.2），随 `media.upload` 一起进库 | 补丁到达后渲染层解码实测 | 无（测不到就不显示秒数） |
| `peaks` | 录音时 `AnalyserNode` 实时采样抽 24 格，随 `media.upload` 进库 | 与 `durMs` 同一次解码算出 | 旧数据/没采到 → 首播时解码回写 |

为什么 peaks 以 `AnalyserNode` 为主：v3 写成"只有 `decodeAudioData` 能给出"，可 9.2 里录音时
本来就挂着 `AnalyserNode`——现场就能算，没道理把字节落库、再取回来解码一次。
实时那一路就是你按住说话时看到的波形，发送那一刻它已经就绪，气泡出现就带形状，不用等回写。
`decodeAudioData` 退到两个它不可替代的位置：**(a)** 旧数据兜底，**(b)** 出站音频唯一的手段
（内核和插件都没有解码器，只有渲染层能解码）。

回填与预取：

- 出站补丁（`pending → ready`）到达后，渲染层**立刻**后台 `media.load` 一次 → 解码 →
  算 `peaks` 与实测 `durMs` → `media.meta.set { messageId, durMs, peaks }` 回写。
  这是同 id 的第二次补丁，不重挂元素（9.4）；之后所有渲染读库，重载一致。
- 预取失败（mime 不支持解码、切会话取消了）不阻塞播放：`<audio>` 直接播字节，
  时长与波形退化成"灰格 + 播完才知道长度"。回写是幂等 UPDATE，失败只影响显示。
- 入站不做这次预取（`media.upload` 已带两个值）。**不做本地缓存兜底**
  （v1 那条"播放时测一下放本地"重载即丢，删）。

界面规则：

- `ready` 才挂条（5.1）；`missing` 显示灰色「语音文件已丢失」；有 `error` 且无 `transcript`
  显示红字与「重试」（`media.retry`）。
- **宽度**：`peaks.length === 0 || durMs === 0` → 固定 80px（最短）且**不显示秒数**（不是 `0:00`）；
  有值时按时长线性映射，80–240px。回填补丁会带来一次宽度跳变，用 CSS 过渡吸收，
  不做"先占位再消失"。
- **展开区有两种标题**，这是"一段语音挂在第一条气泡上"能解释的关键：
  入站写「展开文字」，内容是 ASR 转写（机器听写，可能错，`transcriptKind: "asr"`）；
  出站写「朗读稿」，内容是整条回复的读法（10.2），**与这条气泡的 `text` 不同源、通常更长**，
  因为一段语音对应的是整条回复而不是第一个 part（7.4）。
  副标题固定一句「这条回复合成成了一段语音」，回答"为什么条在第一条、字散在后面几条"。
  一条回复被分成多分时，只有第一条带播放条，后续气泡不加任何入口——避免同一声音出现两个按钮。
- 播放进度用 `requestAnimationFrame` 写 DOM，不进 React state 每帧更新（9.4 第 3 条）。

播放：`media.load` → base64 → `Blob` → `URL.createObjectURL`，渲染层按 `messageId` 做 LRU（约 8 条），
卸载与切会话时 `revokeObjectURL`。IPC 复用 `window.anteros.invoke`，不开新通道，preload 不动
（`invoke` 是按 `KernelMethod` 泛型的，加方法不需要同步改 preload）。

### 9.4 补丁不能让 `<audio>` 重挂

`event.message` 重推同 id 会让 `Bubble` 用新对象重渲染。若 `VoiceBar` 因此重建，
`<audio>` 元素换掉，正在播的语音会**断**。定死三条：

1. 列表里给 `Bubble`/`VoiceBar` 用 `key={message.id}`，且 `VoiceBar` 用 `React.memo`
   比较 `attachment.state/path/peaks`，纯文本变化不触发重挂；
2. `src` 存 `useRef` + `useEffect`，只在 **path 变化**时换 `srcObject`，其余字段变化不动元素；
3. 播放进度不进 React state 的每帧更新（用 `requestAnimationFrame` 写 DOM），
   避免播一条语音就把整屏重排。

### 9.5 `media.status` 只读缓存

pointerdown 时现调 `plugin.health.check` 最坏等一次插件往返（健康检查周期 30s、调用默认超时 10s）。
内核 `media.status` 直接读 `PluginInfo.health`（已在快照里），客户端订阅 `event.plugin` 保鲜。
按钮置灰是本地判断，零延迟。

`media.status` 的返回里带三样，客户端**一样都不自己算**：`listenReady/speakReady`（能力）、
`message`（人话原因）、`asrAffordable`（本月还花得起这一笔吗，10.6）。
预算与已花金额以内核为准——这跟 9.3 里"时长不许客户端自己估"是同一条纪律。

### 9.6 权限

- 主进程现在**没有**任何 `setPermissionRequestHandler`/`setPermissionCheckHandler`
  （`packages/client/src/main/index.ts` 全文搜不到）。既然要开麦克风，就明确只放行 `media`，其余拒绝。
- Windows「设置 → 隐私和安全性 → 麦克风 → 允许桌面应用访问麦克风」关闭时
  `getUserMedia` 抛 `NotAllowedError`，页面里没有权限入口。文案必须点名这条系统设置，不能只写「麦克风不可用」。

## 10. 产品层：什么时候发语音、怎么读才像人

这一节是 v3 新增的，因为 v2 只在讨论"消息附件"，而这次真正要买的是"听起来像人"。

### 10.1 发语音的策略（替掉 `off / always / keyword`）

`keyword` 是个玩具：它把"什么时候该用语音"这种语气判断交给字符串匹配。改成内核里的一个纯函数
`expression/voicePolicy.ts`（新，约 60 行），输入它本来就拿得到的东西：

```
决定 shouldSpeak(reply, state):
  硬门槛
    - 插件 speakReady === false            → 不发
    - 会话是外部通道（不是客户端会话）      → 不发（那边发不出音频，别造成两边不一致）
    - presence ∈ { sleep, busy }           → 不发（对方不可能在听）
    - fullText.length > 56 字              → 不发（长内容该打字；见下）
    - 本轮是降级回复（model = unconfigured/unavailable）→ 不发
  档位（settings: media.voiceOutbound = off | auto | always，默认 auto；2026-11 起按用户要求默认开口，
在「表达」面板里三档可切）
    - off    → 只有明确点「用语音回」才发（本期不做这个入口，等于全关）
    - auto   → 满足下面任一：
         · fullText.length ≤ 24 且 relation.stage ∈ { familiar, close }
         · |moodValence| ≥ 0.4 或 moodArousal ≥ 0.6，且 fullText.length ≤ 40
         · trigger ∈ {proactive, impulse} 且 fullText.length ≤ 32
         · stage === "repairing"（道歉、解释时语气比字有用）
       其余不发；strained 不发语音（这个阶段先发文字）。
    - always → 除硬门槛外都发
```

为什么是 24 / 40 / 56 这三个数：`planner.ts` → `MAX_PART_CHARS = 32`、
`MAX_PARTS = 20`，一次回复常见 1–3 条。56 字大约是两个气泡；超过三十字的口语已经像念稿。
阈值写成 `voicePolicy.ts` 顶部的常量，附一句"改数前先重跑 10.4 的试听"。

关系阶段取 `RelationStage`（`stranger / acquainted / familiar / close / strained / repairing`），
情绪与在场取 `WorldState.moodValence / moodArousal / energy / presence`。这些内核都已有，
不需要新采集任何东西。

### 10.2 朗读稿层（不能拿展示文本去合成）

展示文本被**故意**做成几乎没有标点：`persona.speechStyle.punctuation` 允许 `"minimal"`，
`expression/punctuation.ts` → `polishPunctuation` 的文件头记着一条教训——

> v1.0.11 曾试着"帮模型补标点"：句末补「。」、长串里插「，」。结果分条把一句话切在两半时，
> 前半截被补上一个句号，「是在测试我反应快不快嘛」变成「…反应快。不快嘛」，读起来像结巴。
> 现在这一层**只删不加**。

所以：**绝不能用机械补标点给 TTS 造输入**（同一个失败模式，而且分条边界还在）。
也**不能拿单个 part 去合成**。理由不是"分条一定切在半句上"，而是链条本身就是循环的：
`planner.ts` → `semanticChunks` 先按句读（`SENTENCE_SPLIT`）再按子句（`CLAUSE_SPLIT`）切，
**只有当整段一个标点都没有时才退化到 `hardWrap` 按 32 字硬切**——而展示文本恰恰经常不带标点
（`speechStyle.punctuation: "minimal"`）。也就是说：分条切得碎，正是因为没标点；
而没标点的碎句子，读出来一定难听。两个问题同源，只能靠一份独立的朗读稿一起解决。

定：TTS 的输入是一份独立的**朗读稿**，来源是 `ExpressionService.planReply` 出来的
`fullText`（`joinFullText` 用 `\n` 连接，先把 `\n` 换成空格），交给一次很便宜的模型改写：

- 新增 `LlmPort.generate` 的 `purpose` 枚举值 `"speech"`（`contracts.ts` 一行）。
- 提示词硬约束：只做"读法"转换——分句、书面词换口语、数字/时间/单位改成读法、
  删掉打字特有的空格与颜文字；**不许增删信息点，不许加长，不许改人称**。
- 守卫：朗读稿长度 > 原文 × 1.6 → 弃用，直接用原文合成（宁可机械感也不要跑偏）。
- 守卫：改写调用失败 → 用原文，不阻塞。
- 朗读稿同时写进 `attachment.transcript`（出站语音的展开区显示它，标题就是「朗读稿」，9.3），
  并塞进 `turns.ctx_snapshot` 以便回放。气泡正文仍然用 `text`，界面不因此改一个字——
  这也是为什么"展开区与气泡文字不同源"必须在标题上写明白，否则像 bug。

这一层是**只在要发语音时才多调一次**的调用，成本进 10.5 的账，不发给语音就没有这笔钱。

**顺序**：`voicePolicy` → **预算预检（按 `fullText` × 1.6 的上限估，10.6）** → 改写调用 → TTS。
预检必须排在改写之前——改写本身是一次真实的模型调用，
预算已经见底时先花掉它再拦 TTS，等于白花一笔钱买了个用不上的朗读稿。

### 10.3 韵律跟状态联动

`plugin.media.speak` 的 `rate` / `volume` 由内核算，插件只用它拼请求：

```
rate   = 1.0 + 0.12 × moodArousal − 0.10 × (1 − energy)      钳在 [0.85, 1.15]
volume = 0.8 + 0.25 × warmth(人设) + 0.10 × moodValence      钳在 [0.7, 1.0]
```

- 低能量 + 深夜 → 慢、轻；兴奋 → 快一点。范围故意小（±15%）：超出这个区间多数音色会
  变成机器人或卡通腔，spike 里实测再放宽。
- `PersonaTraits` 里**没有**语速维度（`delayMedianMs` 是打字节奏，不是说话节奏），
  所以人设侧暂用 `warmth` 近似；如果试听后发现需要真正的"说话快慢"人格维度，
  那是 `compileBlueprint` 的一次独立扩参，不在本期偷偷塞。
- 停顿：本期只靠朗读稿的标点自然产生，不额外注入 `<break>`（供应商不通用）。

4. 戴耳机听，按 10.5 的验收线打分：**十句里至少七句闭眼听不觉得在读稿**。
5. 结论写进本文档 15 节的表格里（哪家通过、哪家要格式转换、有没有一家过线）。

**决策门**：没有一家过 7/10 → 本期只做"收语音"（P0–P2），出站语音整段推后，
并把结论写成 `docs/语音条-试听.md` 的一节，将来接本地 Piper（走 `runtime_env`）时再翻案。
过线才继续 P4。

### 10.5 成本与预算

音频按秒/字符计费、token 记 0，而 `record()` 只能靠 token 算钱（§3 第 4 条），
意味着**音频消费完全绕过 `checkBudget()` 的硬拒绝和 ¥45 默认月预算**。
改：`record()` 增加可选 `costCny` 与 `estimated`（给了就直接写进 `cost_ledger.cost_cny`，
没给才按 token 算——列已存在，所以只有这一个函数要改），
音频按插件回报的 `costCny` 落账；插件给不出单价时落 `costCny: 0, estimated: true`，
成本页显示「音频成本未计入（未配置单价）」。**记账口径可以缺，绕过预算闸不行。**
这里的 `estimated` 和 5.1 那个被删掉的不是一回事：它标的是**账本里这笔钱是估算的**，
消费者是成本页的这一行提示与 10.6 的预检；`attachment` 里不需要它，因为附件字段只放实测值。
朗读稿那次改写按 `purpose: "speech"` 正常记 token，进同一本账。

### 10.6 预算闸必须能预检下一笔（本轮新增，验收第 6 条取决于它）

现状核实（`services/cost.ts` → `checkBudget`）：

- 它是**无参**的，函数体是 `if (month >= budget) throw EBLOCKED`——"本月**已经**达上限才拦"；
- `ChatService.send` 的调用顺序是 `cost.checkBudget()` 在 `planReply` **之前**，
  `cost.record(...)` 在投递**之后**（10.5 那条链路）。

两件事叠在一起，v3 写的"月预算调到 1 元、单价配好，第二次合成应被 `EBLOCKED`"**不可能发生**：
音频的钱花完才进账，而闸只看账上已有的数——第一笔合成完就记账，第二笔预检时 `month`
还是 0.6，照样放行。真要撞到闸，得等到某笔把 `month` 顶过预算之后的**下一轮**，
也就是"硬上限永远晚一轮"。

改法（约 10 行，比改验收诚实）：给 `checkBudget` 加一个可选的"下一笔要花多少"，
每笔音频在**花钱之前**过闸：

```ts
/** 预算闸：预检下一笔。extraCny 由调用方估算，0 = 只看已花的。 */
checkBudget(extraCny = 0): void {
  const budget = this.settings.get("plan.budgetCny");
  const month = this.monthCny();
  if (month + extraCny >= budget) {
    throw new AnterosError(ERROR_CODES.EBLOCKED,
      `本月已花 ¥${month.toFixed(2)}，再加这笔 ¥${extraCny.toFixed(2)} 会超过上限 ¥${budget.toFixed(2)}`,
      { hint: "在 设置 → 成本 里调整月度预算，或等下月额度重置（成本上限是硬项）" });
  }
}
```

现有调用点全是 `checkBudget()`，默认参数不动它们一个字节，`month >= budget` 的语义原样保留。

估算式放 `packages/shared/src/voice.ts`（纯函数、可单测）：
`estimateSpeakCostCny(fullText, pricePerSecondCny, rate)` =
`ceil(字数 / SPEAK_CHARS_PER_SECOND / rate) × pricePerSecondCny`，
`SPEAK_CHARS_PER_SECOND = 4.5` 是个常量，量级与 `typingMsFor` 的 `rng.float(4, 6)` 字/秒一致
（中文口语约 4 字/秒），P−1 试听时用实测时长校准它；`rate` 取 10.3 算出来的那个倍率。
**这是全文档唯一还留着"估算"的地方**，因为它的作用就是"要不要花这笔钱"，不进契约、不进界面。
插件没配单价时 `pricePerSecondCny = 0` → 预检等于只查已花的，行为与现状一致，不新增拒绝。

**单价从哪来（v3.2 补明，这是本方案唯一新增的读取路径）**：两个单价是 `core.media` 的配置项（8.2），存在插件配置存储里。内核读它**不加新 RPC**——`PluginsService` 手上就有 `info.config`（`setConfig` 与 `syncRuntimeIntoConfig` 都在读写它），`services/media.ts` 注入这个读口即可；`media.status.asrAffordable` 与 `speakReady` 共用同一个 60s 缓存窗口。也不要退回去让插件"在 `plugin.health.check` 里报单价"：那条返回 `{ok,status,message}`，加业务字段等于改插件契约，而且健康检查本身有缓存，改了价要等一轮才生效。

**单价是用户手填的，不是供应商权威**：所以预检的硬上限建立在"用户把价填对了"这个前提上——填偏低会低估、照样超，填 0 就退化成现状（17 节第 1 条）。8.2 的字段说明必须写清"按供应商账单填"。

两处调用与各自的超预算行为（**不对称是有意的**）：

| 场景 | 预检值 | 超预算时 |
| --- | --- | --- |
| 出站 TTS（7.4 的第二道门） | `estimateSpeakCostCny(fullText, 单价, rate) × 1.6` | **不发语音，退成纯文字**；不写附件、不记 error 到界面，只在 `turns` 留痕。用户无感，钱没花 |
| 入站 ASR（`chat.send` 里转写之前） | `ceil(60) × pricePerMinuteCny / 60`（按录音上限估最坏一笔） | **不能吞消息**。`chat.send` 返回 `accepted: false, reason`，界面点名「这个月的语音额度用完了，可以先打字」，并提示可以改预算或等下月。吞掉用户说的话是最坏的错误，比"晚一轮"更坏 |

出站那格乘 1.6 是**朗读稿的守卫上限**（10.2：改写后超过原文 1.6 倍就弃用）。预检排在改写之前，那一刻只有 `fullText` 可估；不乘的话最多低估 60%，边界上照样会超——评审抓的就是这个口径错。

入站这条要花钱在**用户已经说完之后**，所以更糟的体验是"录完才发现不能转写"。
缓解：把可负担性做成 `media.status` 的一个字段（`asrAffordable: boolean`，内核用
`monthCny() + 最坏一笔 ≤ budget` 算好，读缓存零延迟，见 7.1），pointerdown 直接读它置灰并给原因，
不让用户录完才撞墙；`chat.send` 里那次是兜底（预算刚被改小、或上一条语音刚花完）。
客户端**不自己算钱**：预算与已花金额以内核为准，跟 9.5 是同一条纪律。

### 11.1 表

| 情况 | 表现 | 错误码 |
| --- | --- | --- |
| 插件未装/未启用/未授权 | 麦克风置灰 + 「去配置」；它不发语音 | `EBLOCKED` |

红线沿用 `core.media` 占位实现：**任何情况都不假成功、不返回假音频、不返回假 URL**。

### 11.2 ASR 失败：默认不是沉默

v2 定的是"本轮不回复"。评审的纠正对：真人听到一片嘈杂会追问，沉默是最不像人的反应，
而且用户会以为是软件坏了。定：

- `settings` 加一个键 `media.onAsrFail: "ask_again" | "silence"`，**默认 `ask_again`**。
- `ask_again`：**不调模型**（零成本、也不会让模型即兴解释"我没听清"这件事），
  从一个 3 条短句池里随机挑一条（例：「啊？刚才有点听不清」「这条我没听明白，再说一次？」
  「信号好像不太好，你再说一遍？」），照正常投递链路走：
  建 turn、推 typing、按 `planParts` 分条与计时、落 `event.message`、
  `rememberEpisode({source:"it_did"})`、`observeAgentTurn`。
  **唯一区别是文本来自本地池而不是模型。** 同时 `openLoop({ topic: 常量 })`（7.3 已要求记这个环，
  topic 必须是常量，否则现成的按 topic 判重会失效）。本地池这条**不调模型、不调插件**，
  所以它不受 10.6 的预算预检影响——预算花光了也仍然会回一句人话。
- `silence`：`chat.send` 返回 `{ turnId: 0, userMessage, accepted: false, reason }`，
  不建 turn、不进 `planReply`、不烧预算；渲染层按 `accepted:false` 显示「这条没听懂」，不静默。
- 重试走 `media.retry(messageId)`，成功后补一次 `event.message`，然后**照常生成回复**
  （等价于用户重说了这句话，走同一个 `ChatService.send` 后半段）。
- **入站预算不足之后怎么回来**（v3.2 补）：消息行已经落了（`result.userMessage` 里就有，所以它不会消失），`attachment.state` 停在 `pending`、`error` 写「本月语音额度用完了」，气泡显示「未转写」+「重试」——与 ASR 失败同一个按钮、同一个出口。`media.retry` 的适用面因此要覆盖两种情况：**没转写成功**，以及**转写成功但没形成 turn**（预算拦在转写前，重试时预算已恢复就走完整链路）。月度额度重置（每月 1 日 00:00）或用户改大预算后按钮仍可点，不需要用户重说一遍。7.7 的启动扫描对入站 pending 保留重试、对出站 pending 置 `skipped`，与这条同一条纪律。

实现要点：把 `ChatService.send` 里"投递 parts → 记账 → 落 turns → 记忆"这段抽成一个私有方法
（例如 `deliverParts(...)`），`ask_again` 分支和正常分支都调它。别复制粘贴，
那会导致补丁/成本/记忆三条线在两个分支里各腐化一半。

## 12. 合规与安全清单

1. **群友语音默认不转写。** 这不是"多算钱"的问题，是把别人的声音上传到第三方。所以本期定：
   - 只有**你自己在本机按住录的**那条才走 ASR；
   - 别人的语音（本期仅可能来自将来的通道媒体）一律落
     `text = foreignVoicePlaceholder()`，不读文件、不转写、不发给任何外部服务；
     **这条不是假想敌**：`plugin.channel.download_media` 与能力位 `channel.media` 在 1.0.18
     已经存在（`shared/rpc.ts` → `PluginApi`、`host.ts` → `METHOD_CAPABILITY`），
     只是现在没有插件用它取语音。也就是说"把别人的声音取进本机"这条路是通的，
     规则必须先于功能存在，不能等功能做出来再补。
   - 要做，必须是一个**单独的、可撤销的**开关，且开启时走一次确认 token（`confirm.token`），
     不能塞进一次性总同意里蒙过去。
2. **语音的同意走"渠道 + 授权二次确认"，不升全局声明版本**（本轮改判，代价写在下面）。
   c7 原文只覆盖「外部通道所需的密钥、解密后的数据库内容只在本机使用…调用大模型 API 时
   只会发送装配后的对话上下文」（`shared/consent.ts` → `c7`）。语音超出这个范围两件事：
   原始音频（不只是装配后的上下文）outbound 到第三方，以及**别人的声音**。这两件事都要认。

   v3 写的是"`CONSENT_DOC_VERSION` 升版，所有老用户重勾"。核实之后改成现在这条，理由是代价不对等：
   `ConsentService.status()` 的判定是 `row.doc_version === CONSENT_DOC_VERSION`（全局一个常量），
   所以升版 = **每一个用户**（包括从不点麦克风、从不用语音的人）下次启动被挡在声明闸，
   把九条全部重读、逐个勾完才能进应用。用一个全局门禁去给一个默认关闭的可选功能发同意，
   结果就是声明闸变成日常骚扰——而声明闸的严肃性正是它的价值所在。

   定这三条，全部用现成机制：

   | 时点 | 用什么 | 现状核实 |
   | --- | --- | --- |
   | 用户给 `core.media` 授权 `secrets.read:media.api_key` 时 | 一次性确认 token | `host.ts` → `HIGH_RISK_PERMISSION` 命中 `secrets.read:` → `grant()` 调 `consumeConfirm(confirmToken, "plugin.grant", pluginId)`；快照里 `grantNeedsConfirm: true` 已经会把入口标出来。**免费，已实现** |
   | 确认面板的文案 | 把外发范围写进**授权那一步的界面文案**：「启用语音后，你在本机录制的音频、以及要转成语音的文字，会发送到你配置的语音服务；不启用不出本机。别人的语音默认不发送给任何服务。」 | 授权弹窗逐条显示的是 `helpers.tsx` → `describePermission()` 的中文（`PERMISSION_TEXT` 精确表 + `PARAMETERIZED_PERMISSION` 前缀表），所以给 `secrets.read:media.api_key` 加一条是**表里加一行**，不动声明版本 |
   | 群友语音单独开关（12.1） | 另走一次 `confirm.token`，与上面那步分开 | 同上 |

   要做的一点改动：`app.ts` 的 `consent.status` / `consent.revoke` 分发目前把通道**写死成 `"app"`**，
   只有 `accept` 收 `p.channel`。如果将来想要"按渠道看/撤"，那是 5 行；
   **本期不需要**，因为我们不改声明本体。
   `user_consents` 表本来就按 `(user_id, doc_version, channel)` 唯一，渠道级记账的位置是现成的——
   但要说清"现成"的边界：`ConsentService` 的方法都收 `channel` 参数，
   `CONSENT_ITEMS` 与 `CONSENT_DOC_VERSION` 却是全局的（`accept()` 要求所有 `required` 项全勾）。
   所以"渠道级勾选"不是白拿的，真要做得给 media 单独一条 item + 一个渠道版本常量，约 30–40 行。
   本期选授权那一步的确认 token，就是因为它已经存在。

   **如果项目红线坚持升全局版本**（这仍然是作者的决定权，不是技术选型），那就保留 v3 那条，
   但必须连带写清这次升级的代价：所有老用户被挡一次、重读九条、包括完全不用语音的人；
   并且要一次升够（把语音、导出含录音这两件都并进同一版文案），别一个月升两次。
3. **`npm run lint` 会拦你**：`scripts/check-boundaries.mjs` 的 `scopes` 就是
   `packages/kernel/src` 与 `packages/shared/src`，`banned` 是 `/wechat/i` 与 `/微信/`，
   **注释也算**（文件头写着"任何其它出现，含注释里的分支说明，都视为违规"）。
   行级/文件级放行清单只有 `services/wechat.ts`、`shared/consent.ts`、`channel/`、
   `plugin-manifest`，以及 `app.ts`/`settings.ts`/`rpc.ts`/`domain.ts` 里逐行的通道装配。
   所以：语音与外部通道的结合点放 `services/wechat.ts` 或插件里，
   **`services/media.ts` 里连一句"微信语音"的注释都不能写**，它不在任何放行清单上。
4. **导出与删除已完成，只剩验证**：`export.ts` → `collectMedia()` 已把 media 打进包
   （`MAX_MEDIA_BYTES` 单文件上限，超限只记清单并告警），`reset.ts` 已清 media 目录。
5. **隐私：备份即录音**。正因为导出自动带媒体，"把备份包发给别人" = "把全部录音发给别人"。
   P5 在导出确认里明说包含语音文件与体积；`docs/安全.md` 第 1 节的 **不防** 清单里
   那条「用户主动把导出包/数据库文件发给别人」要补一句：导出包现在含语音文件，也就是含录音。
6. **渲染进程不可信**：客户端只提交 `uploadId`（5.2），路径与体积校验在内核侧（7.5），
   不信任任何前端传来的长度与类型。
7. **密钥不入日志与返回值**：`media.api_key` 走现有 SecretStore，`util/log.ts` 的 `sk-*` 脱敏已覆盖；
   插件不要把 Authorization 头打进 stdout。

## 13. 幂等与副作用面（补丁模式的代价）

补丁 = 同一条消息被推 N 次。凡是被推一次就产生副作用的地方都要查。核实结果先记下来：

| 副作用 | 会不会被补丁重复触发 | 证据 |
| --- | --- | --- |
| **未读数** | **会**。`upsertMessage` 在 `exists` 判断之前就 `unread + 1`（仅 `document.hidden` 时）。一条出站语音最多推 3 次（首推 / ready / 元数据回填），后台标签页下就是 +3。**修法是一个 `if (!exists)`，排 P0**——第一次补丁出现在 P2，不能拖到 P4 | `app.ts` → `upsertMessage` |
| **托盘/系统通知** | **不会**。通知只由 `event.notify` 触发，而 `emitEvent("event.notify")` 全仓只有 `services/channels.ts` 两处（新消息进线时），`event.message` 不产生通知 | `grep -rn 'emitEvent("event.notify")' packages/kernel/src` |
| **微信外部重发** | **不会**。外部投递走 `ChatService.send` 的 `onPart` 回调 → `app.ts` 的 `wechat.sendMany(buffered, ...)`，由 `parts` 循环驱动；`event.message` 不在链路上，附件补丁也不在 | `chat.ts` 里 `if (input.onPart)`；`app.ts` 里 `onPart:` / `deliver:` |
| **打字指示器** | **不会**，但有个反向坑：`app.ts` 的 typing 分支把"非 start"一律当 stop，所以新增的 `transcribe` 态若不同步改客户端，指示器会被**关掉**而不是点亮（7.2）。内核侧 `event.typing` 每轮只 start/stop 各一次，补丁推多少次都不碰它 | `app.ts` → `payload.state === "start"` |
| **记忆写入** | **会**（若不做 7.3）。出站语音的附件补丁不改 `text`，但入站转写会改 `text` → 抽取必须只在转写落定后跑一次。`openLoop` 与 episodic 的去重是现成的，条件见 7.3 第 3 条 | 7.3 |
| **正在播的音频** | **会断**（若不做 9.4）。回填补丁（9.3 的第二次）也走同一条路径，所以 9.4 的第 2 条"只在 path 变化时换 `srcObject`"是它的关键 | 9.3 / 9.4 |
| **成本账本** | 不会重复：`cost.record` 只在 `ChatService.send` 的投递后调一次；音频每附件一次。预检（10.6）只读不写，多推几次不改账 | 10.5 / 10.6 |
| **`turns` 行** | 不会：补丁只 UPDATE `messages` | 5.4 |

**验收用例（P2 与 P4 各一道门，写在 14 节）**：把同一条 `event.message` 连推 5 次，要求
未读数不变、通知数不变、外部发送次数不变、正在播的语音不断、`turns` 不新增。

另外 `chat.send` 的幂等键（`idempotency` 表，7 天）只覆盖"同一次发送不产生两轮对话"，
不覆盖附件补丁；`media.upload` 也要带 `eventId`（5.2 的入参里有），否则用户手抖双击
会落两个文件、发两条语音条。

## 14. 验收标准

**可测的：**

1. 录 8s 发出，你和它看到的时长/波形一致（入站的两个值都来自 `media.upload`，9.3）；重启后仍一致。
2. 文字气泡出现时刻不因语音而改变（对照日志时间戳）。
3. 同 id 连推 5 次：未读数、通知数、外部发送次数都不变，播中的语音不断（13 节）。
4. 关掉 `media.voiceOutbound` 后不再产生任何 `plugin.media.speak` 调用（看插件日志）。
5. ASR 失败默认回一句追问，且 `openLoop` 里真有那条环。
6. **预算预检（10.6）**：月预算调到 1 元、`pricePerSecondCny` 配好后
   · 第一次合成成功并入账；
   · **第二次合成在发出请求之前**就被拒（插件日志证明没有第二次 HTTP 调用），这条退成纯文字，
     附件列是 NULL 而不是 `skipped`（根本没试，就不该留一个"试了没成"的痕）。
7. 转写窗口不空：录一条语音发出，从 `event.message` 到回复之间必须有一次
   `event.typing {state:"transcribe"}`（界面显示「正在听写」），随后才是
   `{state:"start"}` → `{state:"stop"}`；且期间没有多余的 stop 把指示器关掉（7.2、13 节）。
   老客户端渲染层没跟上时这条必须 FAIL——它就是用来抓那个 else 分支的。
8. ASR 超时上限是 10s：让 `listen` 挂起不返回（P0.5 那个不联网的假插件就能演，
   不必等真供应商），10s 内必须走 11.2 的追问分支，而不是等到 `chat.send` 的 120s。
9. `openLoop` 幂等：连续发三条听不清的语音，`open_loop` 表里那个 topic 只有**一条**未闭合环（7.3）。
10. 占位符只有一处定义：`grep -rn` 全仓找不到手写的占位符字面量（第 2 节配套规则二），
    客户端乐观气泡与内核回声的 `text` 逐字相等，列表里不出现两条同样的语音。
11. 系统麦克风关闭、插件未启用、缺密钥三种情况的提示各点名自己那一件事。
12. 撤回一条带语音的消息：文件被 GC，界面显示「已撤回」，且没有把气泡文字覆盖成 `undefined`（7.6 的 bug）。
13. 别人的语音不会被发出去：用插件日志证明没有任何 `listen` 调用。
14. 一段语音挂在**第一条**气泡上，展开区标题是「朗读稿」而不是「文字」；一条回复分多分时
    后续气泡没有第二个播放入口（9.3）。
15. `node scripts/verify-voice-baseline.mjs` 在本期合入后 FAIL 项全部变成"已实现"，不再报旧前提。
16. 提交前：`node scripts/validate-plugins.mjs`、`node scripts/check-boundaries.mjs`、`npm run verify` 全绿；
    **schema** v3→v4 迁移对老库幂等，旧消息 `attachment` 为 null 时界面不报错。

**主观的（这一条和上面 15 条同等重要）：**

17. **按 10.4 的同一批 10 条真实回复合成，闭眼听，至少七句不觉得在读稿。**

## 17. 待定决策

只剩四个真正还悬着的（前几轮已经定掉的不再列）：

1. 音频单价：用户在插件 config 手填 `pricePerSecondCny`，还是统一记 0 并在界面标注未计入。

## 17.5 BreezeBlue：默认合成供应商（v1.0.20 起）

用户要求"默认接入 breezeblue 用语音"，所以 `core.media` 升到 0.3.0，合成默认走 Breeze TTS 2。
核实过的事实（来自 `https://docs.breezeblue.ai/openapi.json` 与官网定价）：

| 项 | 值 |
| --- | --- |
| Base URL | `https://api.breeze.blue/v1` |
| 鉴权 | **`xi-api-key: <KEY>`**（不是 Bearer） |
| 合成 | `POST /v1/text-to-speech/{voice_id}?output_format=mp3_24000_128&delivery=sync`，body `{text, model_id:"breeze-tts-2", instructions?, voice_settings:{guidance_scale}}` |
| 音色 | `GET /v1/voices`（`voice_id` 形如 `voc_xeh3w54cqvnp`）；列表为空就是没配 |
| 识别 | **没有**。整份 openapi 里没有任何 speech-to-text / transcriptions 接口 |
| 价格 | 统一 $30 / 100 万字符（≈ ¥216）；按"非空白字符数"计价，不按秒 |

因此内核里两条计价口径并存（`media.ts` 的 `speakCeilingCny`）：按秒（`pricePerSecondCny`）与
按字（`pricePerMillionCharsCny`）取**大者**。按字那一路缺省就是 ¥216——缺省 0 会让 10.6 的预算闸对语音失效。

插件侧三条实现约定：

1. **密钥可选**：`breeze.api_key` 与 `media.api_key` 都写进 `optional_secrets`。
   两家供应商各一把钥匙，任一把缺失都不该把插件挡在门外（否则"只想合成"的用户会被识别密钥卡住）。
   缺什么由 `plugin.health.check` 的 `message` 说清楚，内核 `media.status` 直接转述它的原话。
2. **语言指令由情绪生成**：`prosodyFor` 给出 rate/volume 之后，插件按 `mood{arousal,valence,energy,warmth}`
   拼一段英文 instructions（Breeze 的 instructions 自由文本，英文效果最稳），用户手填的
   `breezeInstructions` 追加在后，不覆盖。
3. **音色自动挑**：`breezeVoiceId` 留空时 `GET /v1/voices?language_code=zh` 取第一个，
   结果按 `baseUrl|language` 缓存；挑不到就明确报"没配音色且自动挑选失败"，不静默降级。

默认恢复/识别仍走 OpenAI 兼容：`baseUrl` + `asrModel` + `media.api_key`。
「表达」面板新增三档（`media.setVoiceOutbound`），默认 `auto`——配好密钥就会开口，但仍看场合。
