# 微信语音条（虚拟声卡方案）

> 状态：**已实现并接入（v1.0.25，默认关闭）**（2026-11-03）
> 目标：Anteros 在微信通道里发出去的是**真语音条**（对方能点开听、显示时长、走微信自己的 SILK 上传），而不是 mp3 文件。
> 实现见 `M0c-验收.md` 第 38 节；实测证据见第 3 节（按住右 Alt 4 秒 → `voicelength=4400`，界面出现绿色语音气泡）。

## 1. 为什么不能直接发

三条独立的拦路：

1. 策略层：`packages/kernel/src/services/voice.ts` 里 `if (ctx.externalChannel) return { action: "off", …"外部通道会话默认不出声" }`，判据是 `packages/kernel/src/services/chat.ts` 的 `externalChannel: conversation !== "app"`。
2. 发送层：`integrations/wechatauto-sidecar/sidecar.py` 的 `method_send` 只接 `text` / `texts`，底层是「粘贴文字 + 回车」，没有任何语音能力；上游 `wechatauto` 的 `guia.py` 也**没有**发语音/按住说话的接口（只有 `send_file`、`download_voice`）。
3. 格式层：微信语音条是 SILK 编码，塞一个 mp3 到聊天框只会变成文件消息。

## 2. 方案：让微信自己录一遍

不碰微信的内存、不注入进程，只做两件事让它以为「你在按住说话」：

```
合成出 wav  →  播放到虚拟声卡的输入端（CABLE Input）
            →  UI 自动化按住「语音」按钮，按住时长 = 音频时长
            → 松开：微信自己采集（CABLE Output）→ 自己编码 SILK → 自己上传 → 语音条
```

好处：客户端全程当黑盒，微信升级不影响；坏处：要装一个驱动、要前台窗口、系统里的其它声音可能被一起录进去。

### 2.1 已就绪的部分

- **驱动已装**：VB-CABLE（`VBCABLE_Driver_Pack43`，签名主体 `CN=Vincent Burel`，Valid），安装包与解包在 `release/vbcable/`。
  端点已出现：
  - 播放端 `CABLE Input (VB-Audio Virtual Cable)`（waveOut 索引 0）
  - 录音端 `CABLE Output (VB-Audio Virtual Cable)`（waveIn 索引 1）
- **播放链路实测可用**：`release/vbc-probe.py` 用 ctypes 调 winmm `waveOut*`，往索引 0 播 2.0s/48kHz 的音频，实际 wall 1.99s，说明「把任意 PCM 打进虚拟线」这条路是通的，且不需要任何第三方音频库。
- **音频格式**：BreezeBlue 的 `output_format` 枚举里有 `wav` / `wav_24000` / `pcm` / `pcm_24000`（官方 openapi 1.0.0 已核）。所以微信通道合成时直接要 **wav**，落盘即可给 `waveOut` 播，**不需要 mp3 解码器**。

### 2.2 还没验的三件事（都必须微信在跑才能试）

1. **语音按钮在哪**：`wechatauto.guia` 没有这个能力，要用它已经封装好的 UIA（`_get_uia()` / `_uia_input_box()` 那套）在聊天窗里找「语音」按钮的元素与屏幕坐标，或者退回固定布局偏移 + OCR 校验。
2. **微信录哪一路**：`语音消息` 的采集源大概率是**系统默认录音设备**（不是微信设置里「音视频通话」的麦克风）。如果要临时切默认设备，用 Core Audio 的 `IPolicyConfig::SetDefaultEndpoint`（comtypes 手写 vtable），用完还原；绝不能让用户手动改系统设置。
3. **按住时长 → 语音条时长**：微信按「按住-松开的间隔」写时长字段。要实测误差（预计要 `+150~300ms` 补偿），并且在对方设备上核对显示时长。

## 3. 已排除的路线（别再走一遍）

- 开源**没有任何**能发 PC 微信语音条的现成项目（`aixed/WeChat-Hook`、`ttttupup/wxhelper`、`lich0821/WeChatFerry`、`TonyChen56/WeChatRobot`、`ljc545w/ComWeChatRobot` 都只能收语音；`Devo919/Gewechat` 有 `POST /message/postVoice` 但已技术归档、只剩客户端示例；`cluic/wxauto` 是 RPA，只有发文件）。
- DLL 注入 + inline hook / 直接调内部发送函数：能把 SILK 塞进去，但要把代码放进 `Weixin.exe` 地址空间，风险和合规都高一个量级。用户已选虚拟声卡。
- 用「立体声混音」代替虚拟线：本机没有这个端点（Realtek 驱动没开），而且会把系统所有声音一起录进去。

## 4. 环境坑（实测记录）

- 本会话的 shell 是受限令牌（`whoami.exe` 都 Access denied），**waveIn 采集直接失败**：`waveInStart` 返回 0 但 `WAVEHDR.dwFlags` 永远停在 `2`（PREPARED），`waveInGetPosition` 卡在 4。用 C# P/Invoke 交叉验证结果相同，真麦克风也一样 → 不是代码问题，是受限令牌没有麦克风能力。**结论：录音链路只能在 Anteros 正常进程（sidecar）里验证，不能在我们自己的 shell 里验证。**
- 同一原因：`schtasks.exe` 起计划任务也 `spawn EPERM`，想绕开受限令牌跑测试这条路走不通。
- `Get-PnpDevice -Class AudioEndpoint` 能看到端点但看不到「已禁用/未插入」的细节，音频设备要用 winmm 的 `waveOutGetDevCapsW` / `waveInGetDevCapsW` 枚举才准（名字会被截成 32 字符，匹配要用前缀）。

## 5. 下一步（按顺序，每步都要能单独验）

1. 微信启动并登录后，用 UIA 把聊天窗的元素树打出来，定位「语音」按钮（存成 `release/probe-wechat-uia.py`）。
2. 只做**按住-松手**（不放音频）：`release/probe-wechat-voice.py` 按住 2 秒松开，看文件传输助手里是否出现一条 2 秒语音条。这一步过了，整个方案就成立。
3. 接音频：按住期间把 wav 播到 CABLE Input，比对语音条时长与音频时长，标定补偿值。
4. 正式接入：
   - `integrations/wechatauto-sidecar/voice_audio.py`（新）：`play_wav_to_device(path, device_hint="CABLE Input")`，winmm + ctypes，返回实际播放时长。
   - `integrations/wechatauto-sidecar/sidecar.py`：新方法 `voice.send{chatUsername, chatTitle, wavPath, durMs}`，复用 `send_lock()` 与 `_run_isolated()`（界面操作一律丢子进程，卡住可杀）。
   - 内核：`packages/kernel/src/services/voice.ts` 放开「外部通道 + 用户显式开启」；`packages/kernel/src/channels/wechat.ts` 加 `sendVoice`；`plugins/core.media` 合成支持 `format: "wav"`。
   - 客户端：通道页加「微信里也用语音条」开关 + 风险说明（会占用前台、可能录进系统声音），默认关闭，owner 专属。
   - 数据：语音条消息 `attachment` 里记 `delivery: "wechat_voice"` 与实测时长，便于回查。
5. 测试：sidecar 单测（`scripts/test-sidecar-*`）、探针（`release/probe-wechat-voice.py`）、`npm test`、打包。

## 6. 风险与红线

- **发错人 0**：语音发送必须复用现有 `_ensure_chat()` 的「切过去确认再发」逻辑，宁可不发也不能发错。
- 前台被占用：发送期间会把微信拉到前台，如果用户正在打字要避开（沿用主动消息的「用户在场不打扰」闸）。
- 隐私：虚拟声卡会把系统其它声音一起录进语音条，只能靠「发送期间静音其它输出」+ 短按住时间压低概率，必须在开关里写清楚。
- 默认关闭：和完全体、外部通道一样，属于用户显式开启的能力。
