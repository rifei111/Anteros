# 安全与隐私

## 1. 威胁模型

Anteros 是**单机、单用户**桌面应用，没有账号体系、没有云端服务。我们防的是：

- 数据文件被顺手拷走、被网盘自动同步、被其他软件扫盘；
- 日志、崩溃信息、插件输出把密钥或聊天内容带出去；
- 用户误启用高风险插件、误授权后不知道自己在授权什么；
- 插件崩溃/失控拖垮客户端，或插件越权访问数据库。

**不防**：

- 拥有本机管理员权限的攻击者（能读进程内存、能读 master key 文件）；
- 能物理接触机器的人；
- 同一 Windows 账户下运行的其他恶意程序（它们和 Anteros 权限相同）；
- 用户主动把导出包/数据库文件发给别人。

这是 v0.1 的诚实边界，不写成"军事级加密"。

## 2. 数据放在哪

默认在 Electron 的 `userData` 目录（Windows 为 `C:\Users\<用户>\AppData\Roaming\Anteros`，
内核由主进程用 `--dataDir` 同一个目录拉起）：

| 路径 | 内容 |
| --- | --- |
| `anteros.sqlite` | 全部结构化数据（消息、记忆、关系、成本、审计、插件状态与授权） |
| `media/` | 媒体文件 |
| `exports/` | 用户主动导出的包 |
| `logs/kernel-YYYY-MM-DD.log` | 内核日志（已脱敏） |
| `master.key` | 本机主密钥（仅当前 Windows 账户可读，权限 0600） |
| `secrets/<插件 id>/<名称>.bin` | 插件密钥密文 |

数据库**不加密**（v0.1）。敏感的是密钥与通道凭据：它们单独加密，且明文只在内存与插件进程环境变量里出现。

## 3. 密钥

- 主密钥：首次启动生成 32 字节随机数，写 `master.key`（`packages/kernel/src/util/crypto.ts` 的
  `loadOrCreateMasterKey`）；也接受 `ANTEROS_MASTER_KEY`（64 位 hex）用于高级部署。
- 插件密钥：`secrets/*.bin`，AES-256-GCM（随机 IV + auth tag），`packages/kernel/src/plugins/secrets.ts`。
- 启动插件时解密，通过环境变量 `ANTEROS_SECRET_<NAME>` 注入；插件用 `readSecret()` 读取。
- 密钥**不进数据库、不进日志、不进返回值**；日志里命中 `sk-*`、`gh*_`、`Bearer`、`password=`、`token=`
  会被脱敏（`util/log.ts`、`plugins/process.ts` 的 `SECRET_PATTERNS`）。
- 插件 stdout/stderr 由内核接管道读取，每路 1MB 环形缓冲，写日志前先脱敏；插件仍不应把密钥打印到
  stdout/stderr（脱敏只是兜底，不是保险）。

**与规范的差异（如实说明）**：规范写的是 Windows DPAPI。真正的 DPAPI 需要原生扩展，v0.1 用
「用户数据目录里的 master key + AES-256-GCM」代替。它防的是文件被拷贝/云盘同步，但**不防**
同一账户下的恶意程序读 `master.key`。代码注释与本文都不把它说成 DPAPI。

## 4. 插件默认拒绝

四层，缺一不可：

1. **manifest 白名单**：能力只允许 13 项、权限只允许普通权限 + 六个参数化前缀，写错一个整份拒绝
   （`packages/shared/src/manifest.ts`）。
2. **能力授权**：`plugin_grants` 没有有效行就拒绝（`plugins/grants.ts` 的 `require`）。启用插件不等于授权能力，
   owner 要逐项授权；`channel.write` 必须先有 `channel.lease`。
3. **启用闸**：声明闸未过、缺密钥、缺租约 → `defaultCanEnable` 拒绝（`plugins/host.ts`:260-286）；
   `proc.*`、`secrets.read:*`、`fs.write:*`、`ui.foreground` 这类高危权限需要一次性 `confirm_token`（60 秒，用掉即废）。
4. **进程隔离**：插件独立进程、拿不到数据库句柄、每帧 token 鉴权、8MB 帧上限、10s/90s 超时、
   每插件在途 8 条；崩溃只影响自己，内核与聊天继续工作。

**诚实说明**：`fs.*` / `proc.*` / `net.allow:*` 目前是**声明 + 授权 + 审计**层面的约束，不是操作系统级沙箱。
插件是本地 Node 进程，内核无法在 OS 层阻止它 `fs.readFile` 任意路径或访问任意域名。v0.1 的边界是
"官方插件遵守声明、非官方插件风险自负"；真正的强制隔离（AppContainer/Job Object/网络白名单）在范围外。
唯一硬强制的是：插件进程**没有数据库路径**、也拿不到内核 token 之外的 IPC 入口。

## 5. 第三方通道（如微信）的风险

- Anteros **不自带、不内置**任何绕过、注入、逆向、Hook、内存偏移/RVA 的实现；
  `plugins/channel.wechat-replica` 是**未就绪骨架**，健康检查返回 `blocked`。启用它不会操作任何客户端。
- 外部通道的通用风险（也写进声明 c4）：读取本机客户端数据、模拟界面操作，可能影响账号安全，
  甚至被平台限制或封禁。是否启用由用户逐项决定，**默认关闭**。
- **用户自装、自用、自担**：第三方通道组件由用户自行安装并授权；Anteros 不代装、不代授权、
  不提供"免封号""防检测"之类能力。
- 启用流程：声明闸 → 体检（`plugin.health.check`）→ 授权能力 → 租约（写动作独占）→ 才允许读写。
- 停用与兜底：一键停用会调 `plugin.channel.disable_and_restore` 并要求插件还原自己造成的改动；
  托盘/快捷键提供 panic stop（`channels.panicStop` / `system.panic`）。
- 不得用 Anteros 规避平台风控、批量骚扰、冒充他人；这些写在声明 c5，使用者承担法律责任。

## 6. 日志与审计

- 内核日志：`logs/kernel-YYYY-MM-DD.log`，进程内保留 500 条环形缓冲给客户端日志面板。
- 默认只记事件与错误，不记消息正文、不记密钥、不记插件明文 stdout/stderr（脱敏后按行记）。
- `audit_log` 记录谁在何时做了什么（授权、撤销、确认 token、插件启停、危险操作），不记录秘密本身。
- 局限：脱敏是正则匹配，覆盖常见 key/token 形态，不能保证 100%；插件在自己的日志里打印密钥仍属违规，
  由插件作者负责。

## 7. 已知弱点（v0.1）

| 弱点 | 影响 | 计划 |
| --- | --- | --- |
| 未接真 DPAPI | 同账户恶意程序可读 `master.key` | 原生扩展，M1 |
| 无 OS 级插件沙箱 | 插件可绕过声明的 fs/net 约束 | AppContainer/Job Object，超出 v0.1 |
| 数据库不加密 | 拷走 sqlite 可读全部聊天与记忆 | 可选 SQLCipher，超出 v0.1 |
| 安装包未签名 | SmartScreen 警告 | 发布前签名 |
| 脱敏靠正则 | 新型密钥格式可能漏 | 逐步加 pattern + 禁止打印密钥的代码审查 |
