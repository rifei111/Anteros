## v0.10.0：头像、重置与主动消息自检

这一版把「看得见的控制权」补齐，都是管理面板里的按钮，不靠改配置文件：

- **自定义头像**（人格页）：选一张本地图片存在本机数据库里，聊天页显示它；没有图片就退回名字首字。你自己的消息不显示头像。
- **重置记忆**（数据页）：列出将清掉多少条记忆、未闭合话题、对话，双击确认后连对话历史一起清。清完再从聊天里问它「我是谁」，它不该知道。
  为什么需要这个：只删单条记忆时，对话历史还在上下文里，它照样"记得"——所以重置必须同时清对话。
- **整体重置**（数据页）：这台电脑上的它回到出厂；可以勾选保留 API Key、插件运行环境、插件配置。
- **卸载软件**（数据页最底下）：调用安装包自带的卸载程序，可勾选是否连数据目录一起删。
- **主动消息自检**（主动消息页）：显示当前档位、间隔、当日额度、静默时段、今天已发几条，并且和聊天页顶部的状态条是同一份数据；「立即检查一次」会真的跑一遍判定，告诉你"排进队列了"还是"被哪道闸拦住了"；「验证一次：主动消息 → 微信」会真发一条带标记的消息到指定会话，如实回报成功或失败原因。
  档位与出口都在页面上，关掉面板再打开不会丢。

## v0.11.0：多模型与人设文档

**多模型**：聊天框顶上多了一个模型选择器，面板里多了「多模型」页签——可以列一串模型（DeepSeek / Kimi / 通义 / 任意 OpenAI 兼容端点），按下拉选当前对话用哪个，也可以给不同任务类别（对话 / 记忆抽取 / 人设编译 / 媒体描述 / 标题）分别指定模型。调度是硬规则：按类别查路由，没配就回落到全局默认，再没配就用 `llm.*` 设置；每次调用记在成本台账里，模型名如实落库。

**人设文档**：人格页可以「生成当前文档」把整个人设渲染成一份 Markdown（基本信息 / 兴趣 / 背景 / 价值观 / 口癖 / 禁忌 + 只读参数表），能导出成文件，也能把改过的文档导入回来。导入是「改」不是「覆盖」：文档里没写到的字段保持原样，参数表不参与导入（手改数值会破坏区间约束）。

**两处修复**：
- 「表达与完全体」白屏：渲染层加了 ErrorBoundary，任何面板抛错都只坏那一块并给出错误文本与「重新加载」，不再整页白屏；同时补了单实例锁（重复打开会聚焦已有窗口，而不是两个进程抢同一个内核管道），并把渲染层报错落进日志便于定位。
- 微信端收不到回复：`send()` 以前在通道没运行时**静默丢弃**消息，界面上看起来就是"只在本地回"。现在会记日志、把原因挂到通道状态上；重置记忆/整体重置之后也会重新对齐一次通道状态。

## v0.12.0：多用户与群聊

**同一台电脑可以同时对几个人说话**。通道页新增「对话对象」：从最近会话里挑谁算「可对话的人/群」，能设「最多同时对话 N 个」（1–8），每个对象单独设回话模式——私聊默认「都回」，群聊默认「只在被 @ 时回」，也可以设成「都回」或「只看不回」。

**消息排队**：同一个人连着发好几句时，回复不会被交叉打断——每个会话一条队列，轮到了再回；队列太长（默认 20 条，可调）才会丢最老的，并把原因记在通道状态里，不静默丢。

**群聊不是私聊**：模型拿到的上下文里会明确写上「这里是群聊」——不要替所有人总结、不要假设别人知道私聊上下文、话更短、别 @ 所有人。群里的消息会带 mentioned 判断（被点名的才回），发出去的回复会带上被回的人。

**聊天页会话切换器**：顶部多了一个下拉，能在「应用内」和各个微信会话之间切换，各自看各自的对话线。

**验证**：内核端到端冒烟 89 项（新增 7 项：上限、私聊默认模式、群默认模式、改模式、移除对象、数量不超上限），vitest 19 文件 112 用例全绿。


## v1.0.2：群聊真的收到了，也看得出是谁在说话

这一个版本修的是 v1.0.0 里两个说得过去、但其实不成立的假设。

**群聊收不到，是因为只盯了一个会话。** 旁路进程原来只按「一个会话」轮询，界面上把群加进对话对象列表也没用——内核把整张清单传下去了，旁路根本没看。现在按清单逐个会话轮询，各自带各自的水位；群与私聊同时盯，互不顶掉。

**群聊分不清谁是谁。** 现在每条群消息都带发送者昵称与微信号（群里显示昵称、私聊不显示），新消息落库时一起写进 `messages.sender_name / sender_id`。界面上按群聊语义重排：你在群里是旁观者，**它的回复在右边**，其他群成员在左边带首字头像和昵称；私聊保持原样。

**顺手修的两个坑**：

- 数据库迁移不幂等：库里如果已经被补过 `sender_name` 列（手工修库、迁移中途断电都会造成），启动会直接报 `duplicate column name` 起不来。现在先查 `PRAGMA table_info` 再加列，并补了 3 个迁移测试。
- 全角写法认不出：`＠昵称`、`昵称：正文` 用的是全角符号，原来既不认 @ 也不剥前缀。现在两种符号都归一。

**验证**：内核冒烟 92 项（新增会话分线 2 项）；vitest 21 文件 119 用例（新增群聊气泡布局 4 项、迁移 3 项）；旁路群聊解析 14 项（`npm run test:sidecar`，本机没装 Python 时自动跳过）。**不谎报的部分**：真机群消息收发要微信在跑、群里真有人说话才能验，我这边只验到「解析、分线、UI 布局」这三层；装好后你在群里 @ 它一句，看通道页「最近读到的」有没有那条，就是最终判据。

## 版本号策略（从 v1.0.0 起）

以前的 0.1 → 0.12 是一周内连滚出来的，数字本身没有信息量，反而让人分不清"这个版本到底重不重要"。从 1.0.0 起按下面的规矩走：

- **主版本（1.x）**：产品形态变了才动，比如"从单机闭环变成可多端"。
- **次版本（1.1、1.2）**：用户能看见的实质能力增加（新通道、新面板、新能力）。
- **修订号（1.0.1）**：只修 bug、只改文案，不加能力。

不再为了"看起来在推进"每周加一个 0.1。发版说明里写清这次到底改了什么，比数字更重要。

## 内置微信通道：怎么确认它真的读到了

体检绿只说明进程和数据库通了，不说明消息进来了。通道页底部有一块「它最近读到的 / 发出的」：

- 点「看最近 20 条收发」，会列出**真的读到的消息**（谁发的、什么内容）和**真的发出去的消息**；
- 发送失败会红色标出原因（通道没开、界面没找到会话、上游报错）；
- 这份记录只存在内存里，重开 Anteros 就清空，不落库、不上传。

群里它也能读：群消息里的 `wxid_xxx:` 前缀会被剥掉，并按自己的昵称/备注判断有没有 @ 自己（`@所有人` 也算）。
## v1.0.4：记忆按人分开，聊天框上方能看见它记得什么

这次修的是「群里的记忆串到私聊」这个真问题，以及它带来的一个可见改进：

- **记忆按对话线存**：数据库加了 `channel_id`（`memory_episodic`），应用内、微信里的每个人、每个群各记各的；召回时只取当前这条线的记忆，跨线不串味。
- **记忆条**：聊天框上方加了一条「它记得关于这条对话的 N 件事」，点开能看到具体条目；换会话就换内容。
- **重构记忆不越线**：召回后按情绪重构出来的记忆会继承原来的 `channel_id`，不会因为重构跑到私聊去。
- 迁移是幂等的：老库升级会补齐 `channel_id` 并回填 `'app'`；缺表也不会让迁移炸。

验证：`npm test` 21 文件 119 用例全绿；`npm run smoke:kernel` **95 项全过**（新增「群会话线的记忆里有群里的对话」「私聊的记忆列表里看不到群里的记忆」「每条记忆都标着自己属于哪条对话线」）；打包产物实机自检报告里能看到记忆条渲染。

## v1.0.11：说话要像人说话（标点 / 断句 / 发送队列）

这一版修的是「话说不利索」和「发到一半切走了」两件事：

- **标点**：模型常把整句写成「今天好累你呢吃了吗」这种一串字，现在分条之后有一层语言策略
  （`packages/kernel/src/expression/punctuation.ts`）：句末按语气补「？」或「。」、一口气超过
  12 个汉字没有任何标点时在转折词前补一个逗号、重复标点收成一个。只补标点，不改词、不扩写。
- **条数**：每条 32 字、最多 6 条（原来是 25 字 3 条），想多说几句不会被截成一句半；
  两句话拼进一条时也会补逗号，不再粘成一句。
- **发送串行**：微信侧同一时刻只允许一个发送在动界面（`send_lock`，跨进程文件锁）。以前两条消息
  会同时去点搜索框，一个刚打开会话 A、另一个已经把消息粘到 B——表现就是「切换聊天异常、
  消息没发出去」。
- **切会话确认**：打开会话后会核对界面上当前停的是不是这个会话，核不上就重试一次，仍不行**放弃发送**
  并如实报「没能切到会话 X」，宁可这条不发，也不发到上一个聊天窗口里。
- **来消息自动切对话**：微信里来消息时聊天界面自动跳到那个人/那个群；在自己对话里打字也会带上
  当前会话线，不再出现「这个对话框里冒出别的对话」。

## v1.0.3：白屏、发错群、会话串线

这一版只修三件事，都是上一条反馈里的真问题：

- **「表达与完全体」不再白屏**：面板读关系台账时假设 `transitionLog` 一定存在，旧数据或旧内核返回的对象里没有这个字段，读 `.length` 就整棵 React 树卸载。现在面板自己兜底成空数组，字段缺失不再等于白屏。顺手把 IPC 监听上限抬高，消掉 `MaxListenersExceededWarning` 噪声。
- **群里的回复不再发到白名单那个人**：旁路发消息时拿「白名单会话的显示名」当兜底目标，目标是群的时候就会搜错人、发到私聊去。现在按目标 wxid 现解析会话显示名（群也能解析），解析不出来就只按 wxid 搜，绝不再拿白名单标题凑数。
- **群消息不再串到私聊**：推送过来的消息带了会话线（`channelId`），界面原来不分线一律往当前列表塞。现在只收当前会话线的消息，别的会话线只记未读；切过去时重新拉历史。

## v1.0.5：不回旧消息、群后私聊还能回、切会话不丢记录、关系真的归零

这一版修的是「用久了才暴露」的四件事，外加一个它自己的判断权。

**1. 清空记忆后不再一条条回旧通知。** 之前清空记忆和聊天记录，微信里没读过的消息还堆着，
一启动就把它们当成新消息逐条回（日志里能看到连续回「1」）。现在重置时会把已有的未读当成
「开启时的那道水位」，清完不会再补回；旁路重启时也不再退回到从 0 号消息开始读。

**2. 发送卡住不再拖死整条通道。** 微信界面偶尔会卡在搜索框，发一条要等满 60 秒，连着几条
就把旁路堵死，表现就是「群聊说完，私聊没反应」。现在发送带 20 秒看门狗，超时就作废这次并
把 GUI 句柄丢掉重建；内核连着失败两次会进入冷却，界面上会显示「连续发送失败，先歇 N 秒」。

**3. 切换会话不再清空聊天记录。** 会话历史现在按会话线缓存：切走再切回来立刻有内容，
拉取失败也不会把屏幕清空。

**4. 清理/重置记忆时关系归零。** 之前记忆删干净了，亲密、信任、关系阶段还挂着，看起来「一直
在涨」。现在重置记忆会同时把关系退回陌生人（亲密 0、信任 0.5、阶段 stranger）并把七项驱动
清零。

**5. 它知道自己在哪里说话。** 私聊会明确「只有你们两个人」；群聊会明确「群里有别人，不是跟
你说的就别硬接」。

**6. 群聊里可以「自己决定回不回」。** 通道设置里每个会话有一个模式选择，新增
「自己决定回不回」：它可以选择这次不出声（模型只输出 <不回>，Anteros 就不发，也不留下
一条「它说了但没发出去」的记录）。被点名、被直接问通常还会回。

## v1.0.6：通道不再卡死，也不再重发

- 发送/预热放进独立子进程并带硬超时（发送 20 秒、预热 25 秒）：界面卡住只丢这一条，不拖死整条通道。
- 发送前恢复微信窗口（最小化或被挪到屏幕外时必卡，实测矩形是 -31991/-32000）。
- 「消息已操作发送、但数据库未确认」不再当失败重发：这正是「同一条消息发两遍」的来源。
- 打开会话后直接在当前会话发送，不再重复搜索（每条约 6.5 秒）。

## v1.0.7：内置通道真的能启动了

1.0.6 发出去的包有个低级错误：旁路进程里我把打开文件的变量叫了 `handle`，和 JSON-RPC 入口函数 `handle()` 同名，于是 Python 把整个 `main()` 里的 `handle` 当成未赋值的局部变量——进程启动 157 毫秒后带着 `UnboundLocalError` 退出，通道页显示「正在启动 / 已开启但没跑起来」，详情里那句「上次失败：旁路进程退出（code=1 signal=null）」就是它。

修法是把变量改名 `file_handle`，并在旁边留一行注释说明为什么不能叫 `handle`。

## v1.0.8：收不到微信消息（会话标识没归一）

1.0.6 起巡检改成「一次盯多个会话」，但我把设置里写的会话标识（比如微信号 微信号 `rifei111` 这种写法）原样丢给了上游的 `get_new_messages()`，而上游只认 `wxid_xxx` / `xxx@chatroom`。表现极具迷惑性：通道状态正常、体检全绿、日志不报错，就是一条消息都读不到。

修法是巡检前先对每个会话做一次归一（先昵称、再微信号、最后保留原值），结果按调用缓存；水位键仍用原始标识，避免水位错位。日志里会多一行「巡检会话归一：rifei111 → wxid_xxx」方便对账。

## v1.0.18：同步到微信时也是一条一条发

主动消息同步到外部会话时，以前是把所有气泡用换行拼成一段再发出去，
对方那边收到的是一大坨。现在按气泡逐条发：

  这次只是把拼好的整段话换成数组传进去。

验证：`node release/probe-proactive-wechat.mjs`（真内核 + 假旁路进程，不需要真微信）——
应用内 3 条气泡 → 假旁路收到 1 次 `send`，`texts` 长 3：
`在忙什么呢 ⏎ 我刚泡了杯茶 ⏎ 突然有点想跟你说句话`。


推理模型有时会把思维链写进正文（实测到的是残缺的 `<think` / `</think` 加几行旁白），
内核以前直接把它当气泡发了。现在生成后统一清洗：

- 成对的 `<think|thinking|reasoning|analysis|scratchpad>` 整段删；只开了没闭的，从开标签删到结尾。
- `【思考】…【/思考】`、行首「思考过程：」标签删。
- 开头的整行括号旁白删（`（对方这么问，可能是有点认真了吧。` 这种），但 `（笑）` 这类短的保留。
- 清洗后如果只剩空正文，报「模型只返回了思考过程，没有正文」，不发空气泡。
- 提示词里也加了一条：只写要发出去的话，不写分析旁白、不用尖括号标签。

验证：`node release/probe-think.mjs` 用假模型回放实测那种坏串，只发出 1 条正文气泡。

> 想清掉可以去「数据」页清空聊天记录。


这一版只修「平时看不见的东西」：七个内部驱动与主动消息的闸门。

- **五个驱动的稳态值低于阈值**：`rate/(rate+decay)` 才是每个驱动的稳态上限。原来 boredom / tension / fatigue / urgeToShare / anxiety 的稳态都低于自己的阈值，意味着它们永远不可能越阈——驱动算了等于没算。现在七个驱动的稳态都高于阈值（新增回归测试盯着这条），并给参数加了版本号，升级后旧库里那套参数会自动作废重算。
- **陌生人阶段一票否决**：原来 `if (relation.stage === "stranger") return false;`，新用户永远收不到第一条主动消息。现在改成有条件破冰：聊够 3 句、距上次说话 ≥3 小时、当日主动 ≤1 条、想/闷 ≥45%。
- **闸门不再黑箱**：`proactive.summary` 多一个 `blockedBy`，管理面板「主动消息」页新增「为什么现在不发」，直接写最近一次被什么挡住（静默时段 / 频次 / 当日额度 / 陌生人阶段 / 没由头）。
- 自检：「立即检查一次」勾「忽略闸门」时，没有自然由头也会用它的内部状态（想你 / 闷）造一个，保证端到端能验出结果。
## v1.0.15：一行就是一条消息，气泡不再黏成一坨

**真问题（两个，同一个根因）**：你说「气泡上限还是 3 条」「气泡都黏在一起不是一句一句发的」。
从你的真实库里捞出来的样子是这样的——一条气泡里塞着四行：

```
可以的呀
那我一句一句来
你要不先告诉我怎么称呼你
不然我真的猜
```
下一条接着「不出你是谁呀」——**从词中间劈开**。

根因：模型本来就是一行说一句话，但 v1.0.13 改断句规则时把「换行」这个断点弄丢了，
多行被当成一句话；超过 32 字再从词中间硬切。上限从来不是 3 条，是它只切出 2~3 条。

**改法**：先按行切（一行一条，绝不把两行拼回去），行内再按标点切；收尾的「）」「」」挂回前一条，
不再单独成一条；只有超过 20 条才合并。提示词里也写明「每一条单独占一行」。

**验证（真内核 + 本地假模型，4 行输出）**：`node release/probe-parts-mock.mjs` →
4 条独立气泡，打字 0.9–2.7 秒、条间 0.6–2.0 秒。单测 23 文件 136 用例全绿。

## v1.0.19：能收语音条了，也能出声（默认关）

聊天框多了一个麦克风按钮：按住说话（最长 60 秒），松手就发。它收到的是你的声音，但落进对话里的是一句一句的话——

## v1.0.22：网络抖一下不再算「失败」

上一版把 401 说清楚了，但 1.0.21 装上去之后出现的是另一种失败：

```
语音合成失败：插件内部错误：TypeError: fetch failed
```

查下来是**本机到 `api.breeze.blue` 的线路不稳**：这个域名同时有 A 和 AAAA 记录，IPv6 出口时通时不通，
Node 默认按 DNS 返回顺序先连 IPv6，连不上就干等 10 秒的 connect timeout，然后报 `fetch failed`。
实测连打 12 次，有 4 次超时；同一时刻换 IPv4 优先基本一次就过。

改动（`plugins/core.media/index.mjs`）：

- 插件进程启动时 `dns.setDefaultResultOrder("ipv4first")`，优先走 IPv4。
- 网络层失败（connect timeout / TLS / DNS / 连接被重置）**自动重试 2 次**，间隔 0.4s、0.8s；
  超时也参与重试（以前一超时就放弃）。密钥错、参数错这类确定性失败不重试。
- 失败文案带上底层错误码：`网络连不上（UND_ERR_CONNECT_TIMEOUT）：api.breeze.blue 这次没连上，
  本机到它的线路不太稳，过一会儿再点一次「重新生成」`。
- 识别（ASR）侧不重试，因为内核给它的时间窗本来就只有一个 10 秒。

实测：同一台机器上重跑探针，原来必挂的那次现在能穿过抖动打到服务器，并且明确拿到 `HTTP 401`
——也就是说线路问题绕过去了，剩下的 401 是**这把 key 本身不被 BreezeBlue 认**。

## v1.0.23：网络慢不再等于失败

上一版已经加了重试，但实测这台机器到 `api.breeze.blue` 的单次往返在 **1.2 秒到 20 秒**之间跳，
偶尔还会 `connect timeout`；而音色列表只给了 8 秒、试 2 次。结果是：线路只要抖一下，
就报「在 8000ms 内没有响应」，语音永远出不来。

改动（`plugins/core.media/index.mjs` + `packages/kernel/src/services/media.ts` + `plugins/core.media/plugin.json`）：

- **挑中的音色落盘记住**（插件数据目录里的 `breeze-voice.json`）。自动挑音色只会在第一台设备上查一次，
  之后连 `/v1/voices` 都不用打——顺带也省掉一次最容易超时的请求。
- 音色列表超时 8s → **20s**（只试 1 次）；合成超时 90s → **60s**、试 2 次；
  内核等插件的时间 45s → **150s**（语音本来就是异步补上的，多等一会儿比直接判失败强）。
- 健康检查改成**真的打一次只读接口**（`GET /v1/voices?page_size=1`，12 秒），
  所以设置页「它怎么跟你说话」下面那行字现在会直接告诉你卡在哪：
  - 「合成就绪（BreezeBlue·breeze-tts-2，密钥有效，1234ms）」
  - 「合成不可用：BreezeBlue 拒了这把密钥（breeze.api_key 无效或已撤销）」
  - 「合成暂不可用：网络连不上（UND_ERR_CONNECT_TIMEOUT）……」
- 健康检查间隔 30s → 60s、超时 5s → 20s（已经证明这个探测值这个时间）。

装好之后按这个顺序看：设置 → 表达与完全体 →「它怎么跟你说话」。
那行字说「密钥有效」才说明能出声；说「拒了这把密钥」就说明要去 BreezeBlue 后台重新复制一把。

## v1.0.24：声音这一栏，把参数摊开给你看

上一版的问题是"参数藏得太深"：音色、语速、语气强度全在插件的 JSON 配置里，
自动挑音色一旦失败，你看到的只有一句「合成失败」，没有任何地方能改。

这一版在管理面板里新开一栏 **声音**（设置 → 声音），把生效必须的东西摊成控件：

- **状态卡**：一眼看到「能不能说 / 能不能听」，下面一行是内核和插件给的实话
  （密钥有效、被拒、网络连不上，都会原文写在这里），旁边有「重新检测」。
- **供应商**：BreezeBlue（默认，合成）或任意 OpenAI 兼容服务。切换会重启插件。
- **密钥**：`breeze.api_key` 与 `media.api_key` 两栏分开填，已录入的显示「已录入」徽章，
  不会再出现"把合成密钥填进了识别栏"这种事。两把都是可选：缺一把只影响对应能力。

插件 `core.media` 因此升到 0.3.0 并提供 `media.voices` 能力。

之所以要这一栏：BreezeBlue 的默认音色是「自动挑」，而它在国内线路上的往返是 1.2s~20s，
自动挑一旦超时就整条语音失败，用户没有任何入口改成固定音色。现在这个入口有了。

## v1.0.25：微信里也能发真语音条了

以前微信会话里的回复只能是文字：内核里有一条硬门槛「外部通道会话默认不出声」，
旁路进程那边也只能贴文字。这一版把最后一段接上了——**微信里的回复可以发成真语音条**。

做法不是注入、不是改内存、不是逆向协议，而是走微信自己的录音链路：

1. Anteros 合成一段 **wav**（BreezeBlue 直接给 `wav_24000`，省掉 mp3 解码）；
2. 把这段声音播进虚拟声卡 **VB-CABLE**（`CABLE Input`）；
3. 让微信窗口到前台，按住它自己的 **右 Alt「按住说话」**，时长正好等于音频时长；
4. 松开后微信自己编码、自己上传——发出去的就是一条正常的语音条。

于是需要两个前置条件：**装了 VB-CABLE**，并且把 Windows 的默认录音设备设成
**CABLE Output**。设错的话微信会录到房间里的真实声音，所以这一版加了一道自检：
发送前先边播边录测一次电平（RMS 太低直接拒绝发），打开开关时也必须先过自检。

界面在 **设置 → 通道 → 微信** 的最下面：「在微信里发语音条」。默认关闭，开关旁边就是自检按钮。
打开后，一条回复只发一条语音；**语音没合成成功就退回发文字**，不会把话弄丢。

实测证据（`release/voice-lab.py` 实验台）：按住右 Alt 4 秒 + 期间播 3 秒测试音，
微信库里出现 `type=语音 / isSelf=true / voicelength=4400`，界面上是一条绿色语音气泡，
长度约等于按住时长。

## v1.0.26：三个问题一起修

这一版没有新功能，只有三个「说不上崩溃、但用起来很气」的毛病。

**1. 让它发语音，它一直不发。** 原因是两个开关都叫「语音」：声音页那个 `voiceOutbound`
只管应用内，微信语音条另有自己的开关，藏在「通道 → 微信」最底下。你在声音页开到
always，微信里照样静音，日志里只有一句「语音回复没开」。现在：

- 「声音」页也放了这个开关（「外部通道也发语音条」），点开前会先做一次声卡自检，没过不让开；
- 外部通道按语音消息的口径判长度（200 字，而不是应用内的 56 字）——否则多气泡回复
  永远超长、永远不出声；
- 不出声时日志和 `media.status` 会说清是哪一条门槛挡的。

**2. 关系阶段显示不对。** 两个缺陷：每次互动都往「迁移记录」里写一条 `陌生 → 陌生`，
界面上就是一串什么都没变的箭头；另外阶段自动迁移只写库、不推界面，画面一直停在打开时那一刻。
现在记录按 kind 分开（`stage` / `event` / `mode`，界面只显示真迁移），迁移时实时推 `event.relation`。

**3. 一次回复只发出去前三句。** 上游拟人节流（120 秒内写满 6 次就冷却 30–75 秒）把旁路卡住，
内核按「30 秒 + 每段 2 秒」算超时，直接把子进程杀掉；而旁路把「发了 3 条就失败」当成正常
返回，内核又只看 `sent` 不看 `ok:false`，于是界面上六条全是「已发送」。现在：

- 旁路预算 90 秒起、每段 +21.6 秒，内核比它再宽 25 秒，让旁路把真实原因说出来；
- `ok:false` 一律当失败；已发出去几条照实带回来；
- 没发出去的那几条在库里标 `delivery=failed`，界面立刻变红，不再骗人。

验证：`npm test` 26 文件 169 例全绿（新增 4 例）、typecheck / lint / test:sidecar 全过。

## v1.0.27：装好之后自检不再报「找不到 audio_out」

v1.0.26 在应用里点「在微信里发语音条 → 重新自检」会报错：

```
虚拟声卡自检没过，先别开：ModuleNotFoundError: No module named 'audio_out'
```

原因不在虚拟声卡，在我们的便携版 Python。官方 embeddable 包带一个 `python311._pth`，
这个文件一存在，解释器就不再自动把「脚本所在目录」放进 `sys.path`；而 `_pth` 里那行 `.`
又是相对它自己解析的，指向 Python 自己的目录。于是 `sidecar.py` 里 `import audio_out`
必然失败——我在本机调试时手动加过路径，所以没暴露出来。

修法：`sidecar.py` 启动时自己把脚本目录补进 `sys.path`，并且 `audio_out` 走一层兜底加载
（按文件路径 `importlib` 加载），两条路都不通才报错。同时补了一条回归测试：把脚本目录
从 `sys.path` 里摘掉，仍然要能加载 `audio_out`。

装好 1.0.27 后，进【管理面板 → 声音 → 外部通道也发语音条】，点「重新自检」应该看到
「声卡通了，回录 RMS=…」；自检通了才能打开开关。

## v1.0.28：语音条不再「一直卡在生成中」

两条一起改：

1. **正文先发出来，声音后补**。以前气泡一旦带语音，在「生成中」这段就只显示一行
   「语音生成中…」，正文被藏起来——合成慢或失败时，看起来像它突然不说话、界面卡死。
   现在只要语音还没就绪，正文照常显示，声音补上之后再替换。
2. **合成的一分钟之内一定给结论**。BreezeBlue 连不上时不是慢慢变慢，而是一直等到超时：

   现在插件单次 35 秒 × 2 次，内核总闸 90 秒——要么出声，要么明确显示

## v1.0.29：它知道哪句话该用声音说

这一版做四件事。

1. **它自己挑哪句要用声音说**。提示词里给了它一个 `<voice>…</voice>` 标记：想用声音说的那句话
   包起来，一次回复最多一段、一句话（不超过 25 字），留给短、带情绪、想被听见的话。它没标就不出声。
2. **它知道自己发过语音、也知道自己当时说了什么**。历史消息里语音条会带上
   「（我刚用语音说的）」「（他/她用语音说的）」前缀，内容用转写稿——所以它不会再把
   自己用声音说过的话当成没说过，也不会把对方发的语音当成文字。
3. **长文本不再一次合成**。以前把整段话丢给供应商，句子一长就容易崩、也听不出停顿。
   现在按句切开、一句一次合成，再拼回一条 wav（拼不了就只留第一句，正文不受影响）。
   连续的碎句（「嗯。」「好。」）会并到前一句，不为三个字花一次合成钱。
4. **虚拟声卡在「声音」栏里装**，不用再去翻驱动包：面板里能看装没装、缺哪一头，
   点「一键安装虚拟声卡」会弹管理员确认，装完提示重启微信。

同时这一轮又回到多智能体并行：语音自知、声卡检测与安装、客户端面板三块同时动手。

## v1.0.30：它不再永远挑第一句出声

1.0.29 之后暴露了两个小毛病，都修了：

1. **挑哪一句**。以前它没标 `<voice>` 时，代码固定挑第一条——于是不管聊什么都是开头那句出声，
   而真正该用声音说的往往是后面那句（「那我试试看哦」）。现在没标的时候按「短、带情绪、
   结尾是语气词」挑一条；平手时挑靠后的（情绪落点通常在后面，不在开头）。
2. **进闸门的长度**。闸门以前拿整段回复的字数去判「这句该不该出声」，
   于是「整段很长、但只有一句要出声」直接被卡掉。现在按真要念出来的那一句算。

还有一个是它学坏了：它会照抄历史里的「（我刚才用语音说的）」前缀，把那句标注当自己的话说出去。
那个前缀是系统给它的标注，现在发出去之前一律剥掉，提示词里也明说了不要自己写。

## v1.0.31：一句一条

用户 2026-11-04 的要求：长话不要拼成一条语音，拆成一句一句，直接发。改了三处：

1. **合成不再拼**。以前多句会先合成每句、再把 wav 首尾接起来拼成一条（中间还得校验采样率、
   位深一致，拼不上就只剩第一句声音）。现在一句一次合成、一句一条消息，不拼。
2. **可以标多句**。`<voice>` 一次可以标一到三句，每句一个标签；标了几句就有几条语音、
   各自一个气泡。哪句用声音、哪句打字，交给模型自己定（没标的时候才由系统按语气兜底挑一句）。
3. **文字不再被语音吞掉**。以前一旦决定出声，整段回复都不打字了；现在标了语音的那几句发语音，
   没标的照常打字，按原顺序走——微信里就是「一句文字、一条语音、一句文字」。

另外把「挑句子」的闸门改成逐句判：长回复里只有一句该出声时，不会因为整段字数超标被卡掉。

真机探针 `release/probe-multivoice.mjs`（假模型 + 假 BreezeBlue + 真内核）21 项断言全过：
四条气泡、两声两字、每声单独一次合成调用、成本一句一笔、音频各自落盘。

## v1.0.32：语音条真的发得出去

上一版留了两个坑，这一版都填了：

1. **发出去的语音被当成没发出去**。旁路发完语音要回读微信库确认，以前看的是"最新一条消息"——
   可最新一条往往是刚发出去的文字，于是把成功的语音判成失败，又退回发一遍文字。
   现在按下之前先记一个水位，只看这之后新冒出来的消息。
2. **嘴上说不好意思发、手上照发**。同一段回复里既说"不太好意思发"，又把另一句标成语音发出去。
   现在带这类话的句子即使被标了也不出声。

另外一个真机根因：注入右 Alt 用的是 SendInput，微信的键盘钩子不认它（还会让输入框失去焦点），
换成 keybd_event + 扩展键标志就认了。发之前还会核对当前会话标题，对不上直接放弃，绝不发错人。

## v1.0.33：语音落在该落的地方

上一版之后的真机聊天里它这样回：

```
你这是跟我讲条件呀
好嘛好嘛
我手机里其实有一段以前随手录的
就是有点傻哦
[语音] 不过先说好，别笑我。
```

人不是这么说话的。铺垫那句（先说好、别笑我）应该打字，语音该是**后面那句真正要说的话**；
要是还没想好、该等对方先回，这一轮就不该发语音。这一版按这个顺序改了：铺垫留文字，语音往后挪到第一句真内容，
后面没内容就不出声。提示词里也补了三条——它本来就能说话（不用"录"、别说自己只能打字），
对方要语音时把铺垫和正文分开，没想好就别急着发。

## v1.0.34：留着没说出口的话

用户 2026-11-04 确认的第三条路：它想用声音说、但觉得现在不是时候，可以**攒着**。

以前它只有两个选择：这轮说，或者这轮不说就当没想过。现在多一个：

- `<voice>那我试试看哦</voice>` —— 这轮立刻用声音说（老行为，最常用）；
- `<voice wait>那我试试看哦</voice>` —— 这一轮一个字都不发，把这句话存起来；
- 什么都不标 —— 就是打字。

攒下来的那句，对方回话之后系统会摆到它面前：「你上一轮留着没说出口的一句话」。接下来是它自己
决定：现在说出来（用 `<voice>` 标）、或者就算了（不用交代、不用解释，人也是这样的）。

攒着的话有保鲜期：最多被摆三次、最多三十分钟，过时就作废——不能让一句半个月前的台词突然
蹦出来。说得太久的场面话不如不说，这是刻意的。

管理面板「记忆」页多了一栏「留着没说出口的话」：看得到它攒了什么、摆到它面前几次、可以手动作废。

## v1.0.35：人格草案不再"解析失败"

用户 2026-11-04 报：编译人格内核时提示「模型输出解析失败」。根因不是格式，是**话没说完**。

编译的请求写死了 `max_tokens: 900`，而这个结构里有 background 加最多 20 条 rationale；推理
模型的思考过程也占这份额度，于是一句话没写完就被截断——半个 JSON 交给 `JSON.parse`，报出来的
当然就是"解析失败"，然后整份退回规则引擎。

现在这样处理：

1. **预算先给够**：第一遍 1800 token，不够再翻到 3000。
2. **看得出"没说完"**：读上游的 `finish_reason`，`length` 就是被截断，和"格式写歪了"分开说。
3. **截断也会重试**：换一段"更短、更紧凑"的要求再要一次，放弃一部分细节换一份完整的人格；
   重试的 token 一并记成本，不会只记一半。
4. **重试失败也不白费**：把第一遍已经写完的那部分收下来（补右括号、丢掉半截字段），剩下的用
   规则引擎填，提示里写明"按写完的部分解析"。
5. **顺手修格式**：模型自带的 Markdown 围栏、尾逗号、中文引号/冒号、整体单引号，都能救回来。

真机探针 `release/probe-persona.mjs`（假模型 + 真内核）13 项断言全过：第一次回半截 JSON 会触发
重试、两次预算分别是 1800/3000、最终用模型结果而不是规则结果、两次 token 之和进成本。

## v1.1.3：搜索框不再乱闪、"正在写"会自己收、语音发不出去不留假气泡

四个报障、四个根因。

**一、发完文字再发语音，又去搜一次会话。** 旁路每发一条都先 `open_chat()`——搜索、点按、再等
列表刷新。现在发之前先看界面当前开的是谁：标题对得上就直接发，一次都不搜。

**二、声音页选"纯文字"，界面还是生成了一条语音。** 语音合成的总闸只看"有没有开语音"，没看
"是不是被档位关掉了"。现在档位为关闭时，外部通道也不发语音，界面也不会出现语音气泡。

**三、"正在输入中"一直转。** 内核在投递循环里中途抛错时，收尾的 `stop` 事件被跳过了。现在整个
循环包在 `try/finally` 里，不管怎么炸都发一次 `stop`；客户端另外按 `conversation` 过滤（别让
别人的对话在本会话里显示"正在写"），并在一次发送结束后兜底清掉。

**四、群聊里我自己发的话被当成群成员。** 群聊视图把"不是它说的"一律摆到左边、贴上"群成员"。
现在先认"这条是不是我发的"（没有发送者信息就是我自己），我发的仍在右边、不带昵称。

**顺带：一个气泡生成完就直接发出去。** 以前整段写完才一起发，用户等的是"全部写完"的时间；
现在每写好一条就转出去（但第一条语音之后不再抢跑，免得后面的文字抢在语音前面，读起来顺序乱）。
语音发送失败时，界面上的语音气泡会被撤掉并退回发文字——以前只退回文字，气泡留着，看着像没发出去。

验证：`npm test` 27 文件 195 例绿、typecheck 三包绿、边界检查 ok；`package-check` 25 通过 0 警告 0 错误。

## v1.1.4：发一条字不再搜一次

**现象。** v1.1.3 把"写好一条就转一条"做出来之后，新问题冒头：每发一条文字，微信界面上
搜索框就被点开一次；一句回复分四条，用户眼前就闪过四次搜索。

**根因。** 每次发送都是一个新的 Python 子进程，`WeChatGUI()` 也是新对象，上游记录的
"当前会话"永远是空的——所以旁路根本读不到"界面上现在开着谁"，只能老实搜一遍。
更何况微信窗口最小化时，连窗口句柄都读不出来。

**改法。** 把"刚发到哪个会话"记在数据目录里的 `wechat-last-chat.json`：发成功后落盘，
下一条消息先看这份记录，两分钟内还是同一个会话就直接发、不搜。界面读得到当前会话名
时以界面为准。真去搜的那一次，成功也会落盘。

**发错人的兜底。** 跳过搜索直接发，万一这两分钟里有人手动把界面切到别的聊天，就会发错人——
所以跳过搜索时，发完立刻回读目标会话的最新一条，确认是自己刚发的那句；对不上就报失败、
清掉记录，宁可让用户看到"未发送"，也不装作发好了。

验证：旁路自测 9 项（含新增"刚发过就不搜"与"记录过期要重搜"两条）、`npm test` 27 文件 195 例绿、
`package-check` 25 通过 0 警告 0 错误。
